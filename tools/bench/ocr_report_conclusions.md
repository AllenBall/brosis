## 3. 结论

### 3.1 1x 分辨率（1728×1117）是否可接受

**分两种内容看，并且「降采样省时间」这个前提本身不成立。**

| 内容类型 | 1x 等效字号 | 宽度折叠 CER（2x → 1x） | 标识符召回（2x → 1x） | 判断 |
|---|---|---|---|---|
| 中英混排正文 | 15.0 px | 0.74% → 0.63% | 22/25 → 23/25 | **可接受** |
| 深色 UI / 终端日志 | 13.0 px | 1.28% → 1.16% | 17/18 → 15/18 | **可接受** |
| 稀疏页 | 22.0 px | 2.35% → 2.35% | 10/10 → 10/10 | **可接受** |
| 密集页 | 11.0 px | 3.40% → 1.85% | 29/36 → 28/36 | **可接受** |
| 代码小字（等宽 11.5 pt） | 11.5 px | 2.07% → **9.42%** | 22/22 → **17/22** | **不可接受** |

- 除代码小字外，1x 的宽度折叠 CER 全在 **0.63%–2.35%**，与 2x 的差异在 ±1.6 pp 以内，标识符召回相差 ≤2 个。也就是说：**对中文正文、UI 文案和终端日志，1x 采集在准确率上是可以接受的。**
- 代码小字是唯一明确不可接受的：折叠 CER 涨到 **4.5 倍**，整行崩坏。实例（同一行，accurate）：
  - 2x：`let mask: UInt32 = 0x8000_0000 | CGImageAlphaInfo.premultipliedFirst.rawValue`
  - 1x：`vet mask: Uints2 = 8×600020| CoLnageA tonaLnTo. premu cuzo tueorLrst.rawva Lue`
- **但是：降采样并不省 OCR 时间。** accurate 的 p50 在 1x 与 2x 之间只差 −6.3% 到 +15.6%，其中 `code_small` 在 1x 反而**慢 15.6%**（726 ms → 840 ms，因为要在糊掉的图上反复试错）。所以「为了省 CPU 把帧缩小一半」这条理由在实测里不成立；降采样只有在要省内存或跨进程传帧时才值得做。
- **MacBook Air 的 2560×1664（0.74×）与 2x 基本没有差别**，个别样式还略好（`code_small` 折叠 CER 2.07% → 1.58%，`dense_page` 3.40% → 1.35%）——轻度重采样把细笔画略微加粗，反而帮了 OCR。0.74× 可以当作安全的缩放上限。

### 3.2 fast 在哪些样式下不可用

**根因（本次实测得到，不是文档抄写）：`fast` 级别只支持 6 种拉丁语言——`en-US, fr-FR, it-IT, de-DE, es-ES, pt-BR`，不支持 `zh-Hans`。** 请求里写了 `zh-Hans` 也不会报错，中文会被硬当成拉丁字母转写。

| 样式 | fast 最好的一档 CER（严格） | fast 标识符召回 | 结论 |
|---|---|---|---|
| 中英混排正文 | 40.05%（2560×1664） | 14/25 | **不可用** |
| 稀疏页 | 49.67%（1728×1117） | 6/10 | **不可用** |
| 密集页 | 23.84%（3456×2234） | 22/36 | **不可用** |
| 深色 UI / 日志 | 24.32%（3456×2234） | 10/18 | **不可用** |
| 代码小字（纯 ASCII 为主） | 9.75%（3456×2234） | **8/22** | **不可用**（CER 尚可，但关键标识符只召回 36%） |

实例（正文首行，fast）：真值 `brosis 项目周报 · 2026 年第 36 周 · 负责人 Allen Qiu` → 识别 `brosisIfjSPJK. 2026 ¢%36FJ . fi* Allen Qiu`。

**结论：brosis 不能用 fast。** fast 的速度优势很大（关掉语言纠错后 p50 只有 {{fast_off_p50_range}}，是 accurate 的 {{acc_over_fast}}），但买不到任何可检索的中文；连最有利的纯 ASCII 代码场景，关键标识符召回也只有 8/22，1x 下更是 1/22。fast 只有在明确已知画面是纯拉丁文本、且只需要「有没有文字」这种粗判断时才有位置。

### 3.3 对代码小字的建议

1. **代码区不要降采样。** 11.5 pt 等宽字在 1x 下折叠 CER 9.42%、标识符召回 17/22；2x 下 2.07%、22/22。若一定要缩，0.74×（Air 原生像素）是安全上限。
2. **落库前必须做全角折叠。** accurate 的中文模型会把代码里的半角标点转成全角：`(`→`（`、`)`→`）`、`:`→`：`、`;`→`；`、`,`→`，`、`{`→`｛`。`code_small` 的严格 CER {{cs_cer_strict}} 里有 **{{cs_pp_total}} pp** 是排版规范化而不是认错字，其中 **{{cs_pp_fullwidth}} pp 才是全角标点折叠**（去空白 {{cs_cer_nows}} → 宽度折叠 {{cs_cer_relaxed}}），另外 **{{cs_pp_ws}} pp 是空白与换行差异**（严格 {{cs_cer_strict}} → 去空白 {{cs_cer_nows}}）；折叠后只剩 {{cs_cer_relaxed}}。不做归一化，FTS5 里 `sqlite3_prepare_v2(db, sql` 永远搜不到。建议：入库时存 NFKC 折叠后的文本用于索引，同时保留原始识别文本用于展示，两者都写进 `observations`。
3. **十六进制、短哈希、内存地址不可靠，且与分辨率无关。** `a3f9c1e` → `a3t9cle`（f→t、1→l），`0x0000000104f2a1c0` → `Ox0000000104f2a1cO`（0→O）。这类 token 没有语言模型可依，2x 也照错。**不要把 commit 短哈希、内存地址、license key 之类当作可检索证据**；需要精确 token 的场景优先走 AX 文本，OCR 只做模糊召回。
4. **大小写会错**：`kTCCServiceScreenCapture` → `KTCCServiceScreenCapture`。检索侧对标识符做大小写不敏感匹配，并对 `0/O`、`1/l/I`、`5/S`、`f/t` 建混淆等价类。
5. **即使 2x accurate，代码区的标识符召回也不是 100%。** 代码小字样式 22/22，但混在密集页里时只有 29/36：长 URL 和长点号链（`CGImageAlphaInfo.premultipliedFirst`、`VNImageRequestHandler(cgImage:`）会被 Vision 拆成多个观测块，拼回来时中间多出空格。所以**代码区应优先用 AX / 编辑器扩展取文本，OCR 只作兜底**；这与评审 F5 对回退条件的要求一致。
6. **不能直接 join 观测块。** `dark_ui` 的 49 行真值被 Vision 切成 **165 个** `VNRecognizedTextObservation`（3.4 块/行），`code_small` 62 行切成 99 块。采集器必须自己按 `boundingBox` 重建阅读顺序（本脚本的做法：按归一化 y 中点降序分带，带宽取半个行距，带内按 x 升序拼接），否则原文顺序会乱。

### 3.4 usesLanguageCorrection 开还是关

开 / 关各 15 组（5 样式 × 3 分辨率）逐组对照，下表的区间由 `ocr_report.py` 直接从 JSON 计算，不是手抄：

| 级别 | 输出是否变化 | CER 变化（开 − 关） | 耗时代价（开 ÷ 关，p50） | 建议 |
|---|---|---|---|---|
| accurate | **{{acc_lc_same}} 组的全部可比指标相同**（编辑距离、归一化字符数、识别块数、漏掉的标识符、首行文本） | {{acc_lc_cer_range}} | {{acc_lc_ratio}}（{{acc_lc_ratio_pct}}，噪声量级） | 关（开着没有任何收益） |
| fast | {{fast_lc_diff}} 组的可比指标不同 | **{{fast_lc_cer_range}}**，无一致改善：最大改善只有 {{fast_lc_cer_best}}，最大恶化 {{fast_lc_cer_worst}} | **{{fast_lc_ratio}}**（最贵一档 {{fast_lc_ratio_worst}}） | 必须关 |

`usesLanguageCorrection = true` 在 accurate 路径上对 zh-Hans + en-US 组合完全没有作用；在 fast 路径上要多花 {{fast_lc_ratio}} 的时间，而 CER 不但没有一致改善，密集页与深色 UI 在 1x 下反而明显变差，最大恶化 {{fast_lc_cer_worst}}。**采集器固定设为 `false`。**

### 3.5 耗时口径修正（直接回应 F6 对 v1 的质疑）

- accurate p50 落在 **{{acc_p50_range}}**，p95 落在 **{{acc_p95_range}}**，`p95 / p50 ≤ {{acc_p95_p50_max}}`——分布很紧，没有长尾。
- **决定 accurate 耗时的是文本量，不是像素数。** 实测每字符 **{{acc_ms_per_char}}**（稀疏页例外：文本太少，固定开销摊到每个字符上是 {{acc_ms_per_char_sparse}}），每识别块 **{{acc_ms_per_obs}}**：稀疏页（306 字符 / 9 块）144 ms，深色日志（2881 字符 / 165 块）1008 ms，而这两张图的像素数完全相同。
- 因此 v1 报告里「1728×1117 更快」的印象，来自它按尺寸重新排版后行数减半（49 行 → 24 行），**不是分辨率带来的**。同源缩放后这个差异消失。
- 本次测的是 `VNImageRequestHandler.perform([request])` 的墙钟时间，**不能归为 ANE 时间**，也**没有**测能耗（按 F6 的要求，能耗要在 E7 用成对负载 + `powermetrics` 单独测，并纳入 WindowServer 和后台处理进程）。
- 素材仍是**合成图**。「真实界面比合成图快 2–4 倍」依旧是未验证假设，不要写进任何结论。

### 3.6 给采集器的可执行参数

- 识别级别 `accurate`，`recognitionLanguages = ["zh-Hans", "en-US"]`，`usesLanguageCorrection = false`。
- 不为省时间降采样；需要省内存时缩放不低于 **0.74×**，代码区不缩放。
- 单帧 OCR 预算（M4 Max，p95）：正文页 ~0.65 s、代码页 ~0.75 s、密集页 ~0.91 s、终端日志 ~1.07 s、稀疏页 ~0.15 s。按 10 s 一帧、平均 0.8 s 计，稳态约占 **8% 的单核**。Air 上未测，需在 E9 补。
- 入库文本做两份：NFKC 折叠归一化后的用于 FTS5 索引，原始识别文本用于展示。
- 精确标识符（哈希、地址、密钥、金额尾数）不要只靠 OCR 兜底；这类查询要能回答，必须有 AX 文本或应用适配规则。

## 5. 复现

```sh
cd tools/bench
swiftc -O -o ~/Library/Caches/brosis-build/ocr/ocr_bench ocr_bench.swift
~/Library/Caches/brosis-build/ocr/ocr_bench \
  --out "$PWD/results" \
  --samples ~/Library/Caches/brosis-build/ocr/samples \
  --runs 12 --warmup 2 --date 2026-09-06
python3 ocr_report.py results/ocr_bench_2026-09-06.json
```

- 全程 720 次 OCR 调用，累计 279 s；整机运行约 7 分钟。
- `--samples` 目录里有每个 样式 × 分辨率 的 PNG，以及每一组的识别结果全文（`hyp/<样式>_<分辨率>_<级别>_lc<0|1>.txt`），可以逐字对照真值。这些文件放缓存目录，**不要放进项目目录**（iCloud Drive）。
- 真值在 `results/ocr_bench_2026-09-06_truth/`，与实际绘制的像素逐行一致（超宽的行在绘制前就被裁剪，裁剪后的字符串才写进真值）。
