## 1. 结论

| 项 | 结果 |
|---|---|
| 运行时随 app 携带（SwiftPM 源码依赖 → 静态链接进单个可执行文件） | **成立**。`mlx-swift-lm 3.31.4` + `mlx-swift 0.31.6` + `swift-transformers 1.3.4`，`otool -L` 只剩系统库，无第三方 dylib |
| `swift build`（命令行）能编出可用的推理运行时 | **不能，缺 Metal 着色器库**。SwiftPM 命令行不编译 `.metal`，跑起来直接 `Failed to load the default metallib`。本次用本机已有的 MLX 0.31.2 wheel 里的 metallib 顶上，正式发版必须装 Metal Toolchain（见 blockers 第 1 条） |
| 模型由 app 自己下载并校验 | **成立**。清单固定 revision + 每文件 sha256，逐文件校验通过才原子入库 |
| 断点续传（HTTP Range） | **成立**。故意先只下 40.00 MiB 再续，服务器返回 **HTTP 206**，最终 sha256 与清单一致 |
| 镜像源可切换 | **成立**。直连 huggingface.co 与 hf-mirror.com 各完整下一遍，两遍 15 个文件的 sha256 全部与清单一致 |
| 本地导入（只复制不引用） | **成立**。619.02 MiB 往返 0.268 s（APFS clone），校验通过，向量与原目录逐位相同 |
| Developer ID + hardened runtime 下能加载 Metal 与权重 | **成立**。签名后的 `.app` 里跑完整基准，语义 / MRL / 确定性三组结果与未签名 CLI 二进制**逐位相同** |
| 需要的 entitlements | **一个都不需要**。`codesign --options runtime` 不带 `--entitlements`，Metal、JIT 编译 kernel、safetensors mmap 全部正常 |
| `codesign --verify --deep --strict` | 通过（`valid on disk` + `satisfies its Designated Requirement`） |
| 公证 | **没做**。钥匙串里没有 `notarytool` 的 `brosis` 配置，需要你做一次性配置（blockers 第 2 条） |
| 可选生成验证（Gemma 4 26B-A4B） | **Swift 侧暂不支持**。mlx-swift-lm 3.31.4 的 Gemma4 只实现了稠密版，遇到 MoE 的 `experts` / `router` 权重直接报 `unhandledKeys`。D19 候选模型需另测 |
| 批量嵌入的内存峰值能压到 Air 的 16 GiB 以内 | **成立，但必须显式限缓存**。不限时 footprint 峰值 **6.21 GiB**（MLX 缓冲池涨到 5.35 GiB 且进程结束前不还）；`--cache-limit-mib 256` 压到 **1.95 GiB**，吞吐只掉 2.8%。见第 3.5 节 |

**E9 判定：路线成立，但多一条硬前提——Metal Toolchain。** D18（app 不内置模型、清单 + 手动下载 + 镜像 + 本地导入）在本机全流程跑通；
D19 的高档位候选（Gemma 4 26B-A4B）在 Swift 运行时上跑不起来，得换成稠密模型或等上游支持。

> **只报 RSS 是错的。** Apple Silicon 统一内存里 Metal 缓冲计入 `phys_footprint` 而不计入 RSS，
> 批量嵌入时 RSS 会把 6.21 GiB 的工作负载报成 766.5 MiB，低估约 8 倍。**决策一律看 footprint。**

| 工作负载 | **峰值 footprint（决策用）** | 峰值 RSS（参考，低估） | MLX GPU 峰值 / 结束时缓冲池 |
|---|---|---|---|

| 同上，`--cache-limit-mib 1024` | **2,761.9 MiB = 2.70 GiB** | 766.8 MiB | 1,443.3 MiB / 1,029.7 MiB |
| 同上，`--cache-limit-mib 256` | **1,992.4 MiB = 1.95 GiB** | 767.0 MiB | 1,443.3 MiB / 260.6 MiB |
| 同上，`--cache-limit-mib 0`（关掉缓冲池） | **1,839.0 MiB = 1.80 GiB** | 767.8 MiB | 1,443.3 MiB / 0 MiB |
| Gemma 4 加载失败那次 | 321.7 MiB | 354.2 MiB | — |

## 3. 嵌入验证（六项）

模型：`mlx-community/Qwen3-Embedding-0.6B-8bit`，revision `407ad2329cd30702720aafe83f74a1ba30fdfbca`，1024 维，
pooling 策略 `last`（仓库里没有 `1_Pooling/config.json`，MLXEmbedders 回落到模型自带的 last-token pooling），
右侧 padding + 按真实长度构造 mask，L2 归一化，不做 layer norm。查询侧加官方 instruct 前缀，文档侧不加。

### 3.1 确定性

| 条件 | 结果 |
|---|---|
| 同一批大小跑两遍，8 条文本 | **8/8 逐元素完全相同**，最大绝对差 **0** |
| 批 8 vs 批 1（同一条文本，不同 padding 长度） | **0/8 相同**，最大绝对差 **4.04 × 10⁻⁴** |

结论：**同样的批构造是确定性的；改批大小会动数值。** 这不是 bug，是 padding 长度变了导致 GPU 归约顺序变。
对 M1 的影响很实：入库的向量必须记下当时的批构造，或者干脆**固定批大小**，否则同一条文本重跑会得到"几乎一样但不相等"的向量，
去重、增量重建、一致性校验都会被这 4×10⁻⁴ 咬到。余弦相似度上的影响约 10⁻⁷ 量级，检索结果不受影响。

### 3.2 语义合理性（每组 10 对，语料见 `tools/e9/Sources/brosis-e9/corpus.json`）

| 组 | 余弦均值 | 标准差 | 最小 | 最大 |
|---|---|---|---|---|
| 中文近义句 | **0.8678** | 0.0699 | 0.7180 | 0.9287 |
| 英文近义句 | **0.8435** | 0.0669 | 0.7243 | 0.9428 |
| 中英互译句 | **0.8148** | 0.0639 | 0.7248 | 0.8791 |
| 无关句 | **0.2360** | 0.0602 | 0.1257 | 0.3052 |

近义组最低 0.7180，无关组最高 0.3052，**两组之间有 0.41 的空档**，没有重叠。跨语言 0.8148 也说明中英混排场景可用。
语料是照 brosis 自己的域写的（采集、OCR、检索、签名、权限），不是通用测试句。

### 3.3 MRL 截断（报告 11.2 第 7 条）

200 条合成"窗口标题 / OCR 行"式文档（中英混排，含代码路径、群聊、网页标题、终端输出、会议记录五类）+ 40 条查询，
以 1024 维的 top-10 为真值，截断后重新 L2 归一化再排序。

| 维度 | Recall@10 均值 | Recall@10 最低 | top-1 一致率 | 40 条里 top-10 完全一致的 |
|---|---|---|---|---|
| 1024（真值） | 1.000 | — | — | 40 |
| **512** | **0.9250** | 0.60 | 0.675 | 18 |
| **256** | **0.9025** | 0.80 | 0.550 | 11 |

结论：**512 维保留 92.5% 的 top-10，256 维保留 90.3%，向量存储可以砍一半到四分之一。**
但 top-1 一致率掉得快（0.675 / 0.550），说明截断主要打乱的是**头部次序**而不是候选集合。
对 brosis 的用法（检索取候选、再用 FTS/精确字段与时间窗复排）影响不大；如果将来直接拿 top-1 当答案，就不要截断。
注意这是**自洽性**指标（和 1024 维比），不是绝对检索质量——绝对质量要等 D12 的真实查询集，E2 那边同理。

### 3.5 首次加载与内存

**首次加载**（进程启动 → 第一条向量）：热态 5 次 0.387 / 0.393 / 0.389 / 0.396 / 0.390 s，均值 **0.391 s**，
其中容器加载 0.346–0.353 s。口径是用 `sysctl KERN_PROC_PID` 拿的**真进程启动时刻**（含 dyld 加载）到第一条向量返回，
不是 `main()` 进入之后才开始算。五次的向量前 8 维逐位相同。原始记录：`results/embed_1..5.json` 与 `embed_*_stderr.txt`。

**内存峰值——本轮修正的口径（评审 F8）。** 上一轮把 `maximum resident set size`（766.5 MiB）当成批量基准的内存峰值报了出去，
这是错的：Apple Silicon 是统一内存，**Metal 的缓冲（包括 MLX 的缓冲池）计入进程的 `phys_footprint`，但不计入 RSS**。
同一次运行里 `/usr/bin/time -l` 自己就同时打印了两行：

```
       803782656  maximum resident set size     ← 766.5 MiB，低估
      6664668480  peak memory footprint         ← 6,355.9 MiB = 6.21 GiB，这才是真的
```

差的那 5,589 MiB（5.46 GiB）绝大部分就是 MLX 的缓冲池：基准跑完时 `Memory.cacheMemory = 5,479.8 MiB`（5.35 GiB），
而 `Memory.activeMemory` 只有 603.8 MiB（就是权重本身）。缓冲池是 MLX 为了复用中间结果留着的，
**默认上限等于 `memoryLimit`（本机约 121.6 GiB，等于不限），进程结束前不会主动还给系统**。

一次默认设置的完整基准，footprint 是这样长起来的：

| 时点 | footprint | RSS | MLX active | MLX cache | MLX peak |
|---|---|---|---|---|---|
| 加载前 | 8.5 MiB | 38.1 MiB | 0 | 0 | 0 |
| 加载完权重 | 680.6 MiB | 733.6 MiB | 603.8 MiB | 0 | 603.8 MiB |
| 第一条向量之后 | 870.0 MiB | 742.8 MiB | 603.8 MiB | 4.2 MiB | 608.0 MiB |
| 跑完吞吐这一项 | 6,151.4 MiB | 753.3 MiB | 603.8 MiB | 5,278.7 MiB | 1,443.3 MiB |
| 基准结束 | **6,355.9 MiB** | 755.0 MiB | 603.8 MiB | **5,479.8 MiB** | 1,443.3 MiB |
| 主动 `Memory.clearCache()` 之后 | **893.3 MiB** | 753.1 MiB | 603.8 MiB | **0** | 1,443.3 MiB |

**RSS 全程几乎不动（733 → 766 MiB），而 footprint 从第一条向量后的 870 MiB 涨到 6,355.9 MiB（7.3 倍）。**
这就是只看 RSS 会得出错误结论的地方。

两条可操作的结论，直接对应 M1 的夜间任务与 D19 的 Air 可行性：

1. **跑完立刻还内存**：`Memory.clearCache()` 一句就把 footprint 从 6,355.9 MiB 拉回 893.3 MiB（缓冲池 5,479.8 → 0 MiB），
   耗时可忽略。夜间批处理跑完必须调它，否则常驻进程会一直占着几 GiB。
2. **批处理期间就压住峰值**：加载模型**之前**设 `Memory.cacheLimit`（本工具的 `--cache-limit-mib`），
   峰值 footprint 与吞吐的取舍见下表——**256 MiB 是本次数据里的甜点**：

| 缓冲池上限 | 峰值 footprint | 相对默认 | 吞吐 | 吞吐代价 |
|---|---|---|---|---|
| 默认（不限） | **6,355.9 MiB = 6.21 GiB** | — | 70.2 条/s | — |
| 1024 MiB | 2,761.9 MiB = 2.70 GiB | −57% | 68.5 条/s | −2.4% |
| **256 MiB** | **1,992.4 MiB = 1.95 GiB** | **−69%** | 68.3 条/s | **−2.8%** |
| 0（关掉） | 1,839.0 MiB = 1.80 GiB | −71% | 65.7 条/s | −6.4% |

对 Air（16 GiB 与系统共享）的含义：**不限缓存的 6.21 GiB 在 16 GiB 机器上是有风险的**（系统 + 浏览器 + brosis 采集端都要吃内存），
限到 256 MiB 后的 1.95 GiB 才是安全区间。Air 上要用同样的 footprint 口径复测，并顺带看 `memory_pressure` 与 swap，见第 7 节。

> 实现说明：程序内取值用 `task_info(mach_task_self_, TASK_VM_INFO, …)` 的 `phys_footprint`（当前）
> 与 `ledger_phys_footprint_peak`（峰值），代码在 `tools/e9/Sources/brosis-e9/Util.swift` 的 `Proc.footprintBytes()` /
> `Proc.peakFootprintBytes()`。峰值与 `/usr/bin/time -l` 的 `peak memory footprint` 逐字节一致，可交叉验证。
> 每个 `memorySnapshot` 现在同时输出 `footprintMiB` / `peakFootprintMiB` / `residentMiB` / `peakResidentMiB`，
> 结果 JSON 里再也不会只剩 RSS。

## 4. Metal 着色器库：本次最大的坑

`swift build`（SwiftPM 命令行）**不编译 `.metal` 源码**——mlx-swift 的 README 自己写着
"SwiftPM (command line) cannot build the Metal shaders"。结果是 CLI 构建出来的二进制一跑就是：

```
MLX error: Failed to load the default metallib. library not found ... at .../mlx-c/mlx/c/array.cpp:232
```

手工补编也走不通，本机没装 Metal Toolchain：

```
$ xcrun metal --version
error: cannot execute tool 'metal' due to missing Metal Toolchain; use: xcodebuild -downloadComponent MetalToolchain
```

按约束不下载这个组件，于是**借用本机已有的 MLX 0.31.2 Python wheel 里的 `mlx.metallib`**
（`~/.lmstudio/.../site-packages/mlx/lib/mlx.metallib`，125,450,136 字节）顶上，GPU 一切正常。
两个必须写清楚的限制：

1. **版本不完全对齐**：mlx-swift 0.31.6 内含的 MLX 是 0.31.1，借来的 metallib 是 0.31.2。
   同一小版本内 kernel 名与签名没变，实测结果与 Python 参考对到 0.999996 余弦，说明没出问题；但这不是可发版的状态。
2. **体积是上限**：wheel 是**非 JIT 构建**，metallib 里塞了全部 kernel；mlx-swift 是 **JIT 构建**，
   只预编 9 个基础 kernel（`arg_reduce` / `conv` / `gemv` / `layer_norm` / `random` / `rms_norm` / `rope` /
   `scaled_dot_product_attention` / `steel_attention`），其余运行时用 `MTLDevice::newLibrary(source:)` 现编。
   所以装上 Metal Toolchain 之后，metallib 应该显著小于 119.64 MiB，**app 体积会明显低于本次的 159.55 MiB**，
   计划 3.11 里"约 100 MB"的估计届时才好验证。

`tools/e9/Support/build_metallib.sh` 已经写好（照抄 mlx 的 CMake flag），装了 Metal Toolchain 之后一条命令就能编出来，
`build_app.sh` 会自动优先用它。

### metallib 在 `.app` 里该放哪

mlx 的查找顺序（`Source/Cmlx/mlx/mlx/backend/metal/device.cpp: load_default_library`）：

1. `<可执行文件目录>/mlx.metallib`
2. `<可执行文件目录>/Resources/mlx.metallib`
3. SwiftPM bundle：主 bundle 与 `NSBundle.allBundles` 各自的 `resourceURL` 下的 `mlx-swift_Cmlx.bundle/default.metallib`
4. `<可执行文件目录>/Resources/default.metallib`
5. 当前目录的 `default.metallib`

第 1 条对 CLI 构建最省事，但**放进 `.app` 会被 codesign 拒**：`Contents/MacOS/` 下的**任何**文件
都被 codesign 当作嵌套代码去校验签名，而 metallib 是 **MTLB 格式**（`file` 报 `MetalLib executable (MacOS), version 1.2.7`，
魔数 `4d54 4c42` = "MTLB"），**不是可以单独签名的 Mach-O**，于是——

```
brosis-e9.app: code object is not signed at all
In subcomponent: .../Contents/MacOS/mlx.metallib
```

（上一轮把原因写成"metallib 是 Mach-O"，不对：**它不是 Mach-O，拒绝的原因是位置而不是格式**。
`Contents/MacOS/` 是可执行代码的地盘，放什么进去都要能被签名。）

改走第 3 条，放 `Contents/Resources/mlx-swift_Cmlx.bundle/default.metallib`（就是 Xcode 构建 SwiftPM 资源 bundle 的标准位置），
codesign 把它当普通资源封进 `_CodeSignature`，`--verify --deep --strict` 直接通过。**这条要写进 M1 的打包脚本。**

### entitlements：一个都不需要

本次**故意不带 `--entitlements`**，`codesign -d --entitlements -` 输出为空。在这种"裸 hardened runtime"下：

- Metal 设备创建、metallib 加载、**运行时用 `newLibrary(source:)` JIT 编译 kernel**：全部正常
- safetensors 权重加载（603.82 MiB）：正常
- URLSession 下载 + 系统代理：正常

（Metal 的 shader JIT 走的是系统的编译服务，不是进程内可写可执行内存，所以不触发 hardened runtime 的 JIT 限制。）

对正式 app 的含义：`app/Support/brosis.entitlements` 现在那两项（`app-sandbox=false`、`automation.apple-events`）是给采集用的，
**加内嵌推理不需要再加任何一项**。

`tools/e9/catalog.json`（同一份也随 app 打进 `Contents/Resources/`）：

sha256 来源分两种，都记在清单里：`model.safetensors` 与 `tokenizer.json` 是 **LFS 文件**，
HF API 的 `tree?recursive=true` 里 `lfs.oid` 本身就是 sha256，直接抄；其余 13 个是普通 git blob，
API 只给 sha1，所以生成脚本把它们下下来自己算（总共 4.32 MiB，很便宜）。生成脚本：`tools/e9/Support/gen_catalog.py`。

清单里第二项是 `gemma-4-26B-A4B-it-QAT-MLX-4bit`，`source: local-import`、`minRAMBytes: 64 GiB`，

下载器（`tools/e9/Sources/brosis-e9/Downloader.swift`）做到的：

- **URLSession + 系统代理**：用默认 `URLSessionConfiguration`，不设 `connectionProxyDictionary`，自动走 `scutil --proxy` 里的设置
- **Range 断点续传**：`.part` 文件 + `Range: bytes=N-`；服务器若返回 200（忽略了 Range）就截断重来
- **镜像**：默认探测直连与镜像各一次（取仓库里最小的文件量往返），直连不比镜像慢 3 倍就用直连；`--force-base` 可强制
- **校验后原子入库**：全部下到 `.staging-<id>-<uuid>/`，逐文件比对字节数与 sha256，全过了才整目录 move 到 `models/<id>/`，
  旧目录先改名备份、成功后再删
- **`installed.json`**：`repoId` / `revision` / `source` / `baseURLUsed` / `totalBytes` / `fileCount` / `installedAt` / `verifiedAt` / `catalogSchemaVersion`

实测的断点续传证据（直连那次，`download.json` 里 `model.safetensors` 这一条）：

```json
{ "path": "model.safetensors", "bytes": 633152041,
  "resumedFromBytes": 41943040,   // 先只下了 40.00 MiB
  "rangeStatus": 206,             // 续传请求服务器答 206 Partial Content
  "seconds": 41.63, "sha256OK": true }
```

`resumedFromBytes = 41943040` 且 `rangeStatus = 206`，最后整文件 sha256 与清单一致——
说明 `Range: bytes=41943040-` 被 HF 的 CDN 正确处理，续传拼出来的文件是对的。
代码里还留了"服务器返回 200（忽略 Range）就截断重下"的兜底分支，本次没有触发。

本地导入往返：把已装目录当源目录导进另一个 models 根，619.02 MiB / 15 个文件 **0.268 s** 校验并入库，
导入后跑同一条文本，向量前 8 维与原目录**逐位相同**。速度这么快是因为 `FileManager.copyItem` 在 APFS 上走 `clonefile`（写时复制），实测：

```
导入前后 df 可用空间只少了 76 KiB，而 du 报告这个目录 633,924 KiB
```

语义上仍是独立副本（源目录被改被删都不影响它），符合 3.11"只复制不引用"的要求；
但**磁盘占用在被改写前是和源目录共享的**，做容量估算时别把导入的副本重复计入，
反过来说，"从 LM Studio 目录导入一个 15.6 GB 的模型"在同一个卷上其实不额外吃盘——
除非之后源目录被删且文件被改写。

## 10. Blockers（需要你操作）

1. **装 Metal Toolchain**（约 GB 级下载，本次按约束没装）：
   ```
   xcodebuild -downloadComponent MetalToolchain
   ```
   装完之后 `tools/e9/build_app.sh` 会自动调 `Support/build_metallib.sh` 编出版本对齐的 `mlx.metallib`，
   届时才能给出**真实的 app 体积**（现在的 159.55 MiB 是借用全量 metallib 的上限）。
   **在这之前 E9 的分发结论只能算"机制验证通过"，不能算"可发版"。**

2. **配 notarytool 凭据**（一次性）。现在：
   ```
   $ xcrun notarytool history --keychain-profile brosis
   Error: No Keychain password item found for profile: brosis
   ```
   两选一（Team ID 固定 `<TEAMID>`）：
   ```
   xcrun notarytool store-credentials brosis --apple-id <你的 Apple ID> \
       --team-id <TEAMID> --password <App 专用密码>
   # 或
   xcrun notarytool store-credentials brosis --key <AuthKey_XXXXXXXX.p8> \
       --key-id <KEY_ID> --issuer <ISSUER_UUID>
   ```
   配好之后（`build_app.sh` 第 9 步会自动检测并打印这几行）：
   ```
   ditto -c -k --keepParent ~/Library/Caches/brosis-build/e9/brosis-e9.app /tmp/brosis-e9.zip
   xcrun notarytool submit /tmp/brosis-e9.zip --keychain-profile brosis --wait
   xcrun stapler staple ~/Library/Caches/brosis-build/e9/brosis-e9.app
   spctl -a -vv -t exec ~/Library/Caches/brosis-build/e9/brosis-e9.app   # 期望 accepted
   ```
   App 专用密码要你自己在 appleid.apple.com 生成并输入，我不碰。

3. **D19 高档位需要重新选型**。Gemma 4 26B-A4B 在 Swift 侧跑不起来（第 8 节）。
   要继续验证 D19，需要你批准下载一个 Swift 侧支持的稠密候选（Qwen3.5-4B MLX 4bit 约 3.4–4 GB，或 Gemma 4 E4B 约 5.9 GB）。
   本次按约束**没有下载任何生成模型**。

4. **真冷启动数字要你来跑一次**：`sudo purge` 需要管理员密码，我没执行，所以**本轮只有热态 0.391 s**，
   冷启动这一格是空的。
   ```
   sudo purge && /usr/bin/time -l <app>/Contents/MacOS/brosis-e9 embed \
        --id Qwen3-Embedding-0.6B-8bit --out cold.json
   ```
   或者干脆重启后第一次跑（`--out` 会把结果落盘）。

5. **Air 上复测**（第 7 节清单）。需要你把 app 与模型拷到公司机、或在那边重跑一遍下载。
   **复测第 2 项一定要看 `peak memory footprint` 而不是 `maximum resident set size`**——
   RSS 在这个工作负载上低估约 8 倍（766 MiB vs 6.21 GiB），拿它判断 16 GiB 够不够会得出相反的结论。

## 11. 对计划的修订建议

| 位置 | 现在写的 | 建议改成 |
|---|---|---|
| 3.11 / D18 | "app 体积约 100 MB" | 改成"可执行 40 MiB + Metal 着色器库（JIT 构建，装 Metal Toolchain 后实测）"，等真实 metallib 出来再定数 |
| 3.11 初始清单 | Qwen3-Embedding-0.6B MLX 8bit 约 0.65 GB | 实测 649,088,604 字节 = 619.02 MiB = 0.6045 GiB，与"约 0.65 GB(10⁹)"一致，可保留；建议把 revision `407ad232…` 写进计划 |
| 3.11 初始清单 | Gemma 4 26B-A4B 作为 128 GB 机器的可选高档位 | 加一句"mlx-swift-lm 3.31.4 不支持其 MoE 结构，Swift 运行时暂不可用"，D19 候选收敛到稠密模型 |
| D18 | 未提构建前提 | 加一条"构建机必须装 Metal Toolchain（`xcodebuild -downloadComponent MetalToolchain`），否则 SwiftPM 命令行构建出的运行时无法加载 Metal" |
| 3.4 检索设计 | 未提向量维度 | 可以写"向量按 MRL 截断到 512 维存储，Recall@10 保 92.5%；不要直接用 top-1" |
| 新增风险 | — | "同一文本在不同批大小 / 不同机器上向量不逐位相同（10⁻⁴ 量级），入库与跨设备同步要按余弦阈值比较，不能按字节比较" |
| 3.11 / D19 内存门槛 | 只写了模型体积与"最低内存" | 加一句"**MLX 的缓冲池默认不限，批量嵌入的 footprint 峰值是模型体积的 10 倍量级**（本次 619 MiB 模型 → 6.21 GiB 峰值）；嵌入服务启动时必须设 `Memory.cacheLimit`（建议 256 MiB，吞吐代价 2.8%），批处理结束调 `Memory.clearCache()`" |
| 附录 A / 各实验的内存口径 | 未指定 | 统一写死"内存峰值指 `peak memory footprint`（`/usr/bin/time -l` 同名行 / `task_info(TASK_VM_INFO).ledger_phys_footprint_peak`）；Apple Silicon 上 RSS 不含 Metal 缓冲，只作参考"，避免各实验各报各的 |
