### 一句话结论

**D19 定案的 Qwen3.5-4B MLX 4bit 在 Air 上完全可用：加载 0.8 s、生成 35 tok/s、一次叙述 7 秒、峰值内存 3.42 GiB、磁盘 2.86 GiB、温度 0 逐字确定、JSON 抽取 5/5。唯一必须写进计划的约束是——思考模式在这台机器上跑不完，本地叙述与抽取一律强制 `enable_thinking=false`。**

## 3. 关键数字（含单位口径）

### 3.1 下载与安装

| 指标 | 数值 |
|---|---|
| 源探测 | 直连 `https://huggingface.co` **2.153 s** 通、镜像 `https://hf-mirror.com` **1.721 s** 通；按「直连不比镜像慢 3 倍就用直连」的规则选**直连**（`baseUsed = https://huggingface.co`） |
| 总量 / 耗时 / 速率 | 3,061,132,920 字节 = 2,919.32 MiB，**235.65 s**，**12.39 MiB/s** |
| 其中 `model.safetensors` | 3,034,300,695 字节（2.826 GiB），224.64 s，**12.88 MiB/s** |
| `tokenizer.json` / `vocab.json` | 19.06 MiB @ 4.5 MiB/s；6.41 MiB @ 3.75 MiB/s（小文件被 TLS 握手摊薄） |
| sha256 | **12/12 全部与清单一致**（`sha256OK: true`），其中 2 个来自 LFS oid、10 个由 `gen_catalog.py` 下载后自算 |
| `verify` 重新全量校验 | **1.272 s**，`allMatch: true` |
| `/usr/bin/time -l` 下载进程 | `239.75 real`，**`peak memory footprint = 6,101,898,112 字节 = 5,819.2 MiB`**，RSS 2,885,419,008 字节，`swaps = 0` |
| `du -sk` 安装后 | 2,999,928 KiB = **2,929.62 MiB = 2.861 GiB** |

> **下载与校验的内存峰值（新发现，验收时已修）**：下载一个 2.826 GiB 的文件，进程 footprint 峰值到
> **5,819.2 MiB**；单独 `verify` 这个模型也到 **2,935.8 MiB**。**原因不是"整个响应体攒在内存里"**——`URLSession.download(for:)`
> 本来就是流式落盘，`append` 与 `Hashing.sha256` 也都是 4–8 MiB 一块地读。真正的原因是 `FileHandle.read(upToCount:)` 返回的
> `Data` 是 autorelease 对象，命令行工具主线程没有跑 RunLoop，自动释放池要到循环结束才清空，于是每一块都攒着：
> 下载 = 拷贝 2.8 GiB + 校验 2.8 GiB ≈ 5.8 GiB。**修法是给两个循环体各包一层 `autoreleasepool`**（`Util.swift`、`Downloader.swift`，
> 验收者 2026-09-07 已改并重建）。修复后实测（同一台 Air）：`verify` 2.9 GiB 模型 **2,935.8 → 9.4 MiB**，`verify` 619 MiB 模型
> 625.4 → 9.2 MiB，`download` 619 MiB 模型 **1,239.4 → 29.8 MiB**，耗时不变、sha256 全对。原始文件在验收者的
> scratchpad（`verify/verify_fixed_*.err`、`verify/download_fixed.err`）。M1 的下载器与校验器沿用这个写法即可，不必重写。

### 3.4 思考模式的代价（步骤 c）

同一提示、同一系统指令，**去掉 `--no-think`**：

| `--max-tokens` | `promptTokens` | 生成 token | 生成 tok/s | `stopReason` | 是否出现 `</think>` | 总耗时（`real`） | 峰值 footprint |
|---|---|---|---|---|---|---|---|
| 1,500 | 835 | **1,500（用满）** | 35.47 | **`length`** | **否** | **45.98 s** | 3,676,982,224 字节 = 3,506.6 MiB |
| 4,000（追加验证） | 835 | **4,000（用满）** | 33.36 | **`length`** | **否** | **123.85 s** | 3,668,429,776 字节 = 3,498.5 MiB |

**思考段一次都没结束，因此没有产生任何答案，「答案是否仍在 150 字内」这一问无从谈起。**
1,500 token 那次的输出是英文的 `Thinking Process:` 分析加中文草稿；4,000 token 那次继续在同一个循环里
逐词数中文字数、反复重写同一段草稿（尾部原文见第 4.4 节）。

代价换算（与 3.3 的 `--no-think` 对照）：
- **多花的 token**：≥ 4,000 − 147 = **≥ 3,853 token**，而且还没结束。
- **多花的秒数**：123.85 − 6.82 = **≥ 117.0 s**，即 **≥ 18 倍**，仍然一无所获。
- 内存与 TTFT 与非思考模式**一样**（3,498–3,507 MiB，TTFT 2.63 / 2.80 s）——代价全在生成 token 数上。

**4,000 token 那次结束时热状态从 `nominal` 变成 `fair`**（连续 123.85 s 满负载）。按步骤 g 的要求，
下一项测试前静置约 4 分钟，重测 `thermalState` 回到 `nominal` 后才继续；后续所有运行的
`thermalStateAtStart` 与 `thermalStateAtEnd` **全部是 `nominal`**。

### 3.5 JSON 抽取（步骤 d）

| 1 飞书 | 309 | 65 | 283.4 | 36.13 | 1.104 s | ✅ | 否 | ✅ | ✅ |
| 2 Xcode | 305 | 53 | 283.5 | 36.45 | 1.088 s | ✅ | 否 | ✅ | ✅ |

**5/5 有效；5/5 键集合恰好是 `{apps, topics, people, summary}`（不多不少）；5/5 的 `apps` 全部出自输入，没有编造。**

### 3.6 长输入的预填（步骤 e）

合成长台账：12 个应用的表格 + 15 段会话 + 联系人清单 + 文件清单 + **逐次前台切换记录（每行「时刻 前一个应用 → 后一个应用 · 停留秒数」）**。
命令：`--no-think --temperature 0 --max-tokens 300 --cache-limit-mib 256`。

| 版本 | `promptTokens` | **预填 tok/s** | **TTFT** | 生成 tok | 生成 tok/s | **峰值 footprint** | `real` |
|---|---|---|---|---|---|---|---|
| 837 token（3.3 的叙述） | 837 | 317.4（3 次均值） | 2.651 s | 147 | 35.38 | 3,518.5 MiB | 21.60 s（3 次） |
| 55 条切换记录 | **3,664** | **344.2** | **10.678 s** | 107 | 34.47 | 3,768,814,640 字节 = **3,594.2 MiB = 3.510 GiB** | 15.06 s |
| 130 条切换记录 | **5,354** | **339.6** | **15.802 s** | 128 | 33.40 | 3,866,315,752 字节 = **3,687.2 MiB = 3.601 GiB** | 20.79 s |

要点：

- **预填速率与输入长度基本无关**（317 → 344 → 340 tok/s，837 token 那档偏低是因为固定开销占比大）。所以 **TTFT ≈ prompt token 数 / 340**，可以直接线性外推。
- **内存随输入增长很温和**：3,664 → 5,354 token（+46%）只让峰值 footprint 涨 93.0 MiB（+2.6%）。KV cache 在 4bit / 32 层这个规模下不是内存瓶颈。
- **按 3.42–3.60 GiB 的峰值和 16 GiB 的机器算，输入上限不是内存卡住的，是 TTFT 卡住的**：
  - 8,000 token 输入 → TTFT 约 **23.5 s**；
  - 16,000 token → 约 **47 s**；
  - 32,000 token → 约 **94 s**。
  **建议 M1 把「每天一次叙述」的输入上限定在 8,000 token 以内**（TTFT < 25 s，加生成不到 30 s），超出就先做确定性摘要再喂给模型。262K 的上下文长度在这台机器上是名义值，不是可用值。

### 3.7 缓冲池上限对照（步骤 f）

同一份 3.3 的叙述提示，各跑 1 次（`--repeat 1`），只差 `--cache-limit-mib`：

| 缓冲池上限 | **峰值 footprint（决策用）** | 峰值 RSS（低估） | 跑完时的 footprint / MLX 缓冲池 | `clearCache()` 之后 | 预填 tok/s | 生成 tok/s |
|---|---|---|---|---|---|---|
| **256 MiB** | **3,670,002,664 字节 = 3,500.0 MiB = 3.418 GiB** | 2,647,474,176 字节 = 2,524.8 MiB | 679.3 MiB / **217.7 MiB** | **465.4 MiB** / 0 MiB | 322.7 | 35.74 |
| **默认（15,564.8 MiB，等于不限）** | **4,338,486,464 字节 = 4,137.5 MiB = 4.040 GiB** | 2,647,375,872 字节 = 2,524.7 MiB | 4,137.3 MiB / **1,703.6 MiB** | **516.1 MiB** / 0 MiB | 322.2 | 35.82 |
| 差 | **−637.5 MiB（−15.4%）** | 0.1 MiB | −3,458.0 MiB | — | −0.2% | +0.2% |

- **两档的答案逐字相同**，也与 3.3 的三次逐字相同 —— 限缓存只改内存，不改数值。**结论与嵌入侧完全一致：256 MiB 是免费的。**
- **`Memory.clearCache()` 有效**：不限那档跑完 footprint 4,137.3 MiB → **516.1 MiB**（缓冲池 3,961.4 → 0 MiB）；256 那档 679.3 → 465.4 MiB。D27 的「任务结束清空缓冲池」在生成任务上照样成立。
- **`memoryWithModelLoaded` 这个字段是本轮新加的**：不加 `withExtendedLifetime(container)` 的话，Swift 会在最后一次用到 container 之后立刻释放模型，`memoryAtEnd` 量到的是「已卸载」的数，会让人误以为跑完只占 600 MiB。加了之后才是「模型还在内存里时占多少」：256 档 **2,634.8 MiB**、不限档 **4,137.3 MiB**。
- **swap 与内存压力**：每一步前后都记了 `sysctl vm.swapusage` 与 `memory_pressure`（文件 `sysmem_*_before/after.txt`）。系统 swap 用量在整轮里从 349.25M 降到 317.25M（**没有增长**，变化来自用户自己在用这台机器），`/usr/bin/time -l` 的 `swaps` 全部为 **0**，内存空闲率 58–68%，从未进 warn / critical。**16 GiB 上跑这个模型不进 swap。**

## 7. 对计划的影响（各一句话）

- **D19**：候选重选到此结束——**Qwen3.5-4B MLX 4bit 在 Air 上验证通过**（加载 0.800 s、生成 35.4 tok/s、一次叙述 7 秒、峰值 3.418 GiB、磁盘 2.861 GiB、温度 0 逐字确定），可以把 D19 从「候选需重选」改成「已定并已实测」，同时把**「本地叙述与抽取强制 `enable_thinking=false`」写进决策正文**。
- **D20**：本地通道在生成类任务上已经跑通且够快（一次叙述 7 秒），**线上通道从「叙述的必需退路」降级为「可选加速 / 更强模型」**；3.10 要求的温度 0 与关闭思考两条已在本地实现，剩下的 JSON 校验与失败重试一次仍要在提供方抽象里统一做，本地与线上共用。
- **D27**：结论在生成任务上**原样成立并更干脆**——256 MiB 缓冲池让峰值 footprint 从 4,137.5 MiB 降到 3,500.0 MiB（−15.4%），而预填与生成速率的差都在 0.2% 以内、输出逐字相同，所以「加载前设 256 MiB、任务结束 `clearCache()`」应当作为**所有**本地模型任务（不止嵌入）的默认策略写死。
- **3.10**：表里「温度 0、关闭思考模式、JSON 校验、失败重试一次」的前两条现在有了本地实现与实测依据（`--temperature 0` / `--no-think`，16 次非思考生成无一例外），**建议把「关闭思考模式」从通用要求升级成对 Qwen3.5 的硬性要求并注明理由**（思考模式 4,000 token 不收敛），后两条仍是 M2 待办。
- **3.11**：清单表里 Qwen3.5-4B 那一行的「约 4 GB」应改成**实测 2.851 GiB（`du` 2.861 GiB）**、「最低内存 16 GB」维持，并补一句**「多模态仓库，Swift 只加载文本塔，其中 636.13 MiB 的视觉权重下载后不使用」**；另外「下载器与导入的 M1 要求」要加一条——**逐块读文件的循环必须包 `autoreleasepool`**（修复前下载 2.826 GiB 的文件 footprint 峰值 5,819.2 MiB、校验 2,935.8 MiB；修复后 29.8 MiB / 9.4 MiB，已在 `tools/e9` 修正）。
- **附带一条给 M1 的输入上限**：预填稳定在约 340 tok/s，**叙述的输入上限建议定在 8,000 token（TTFT ≈ 23.5 s）**，262K 的名义上下文在这台机器上不可用，超长台账要先做确定性摘要再喂模型。
