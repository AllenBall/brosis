### 1.3 **最重要的一条口径：入站记录落在哪个 `(device_id, id)`**

3.9 写「不可变记录的主键带 device_id，两边永不碰撞」。schema 从 M1 起就是
`PRIMARY KEY (device_id, id)`，这一点没有变。变的是**入站记录用哪一对**：

> 入站记录以 `device_id = 本机`、`id = 本机计数器新分配的值` 落库，
> 来源 `(origin_device, origin_id)` 记在两个新列上，由部分唯一索引保证只落一次。

**为什么不原样沿用源设备的 `(device_id, id)`**：M1 的检索层与 3.6 的 MCP 协议把 observation
的句柄定死成**一个 Int64**（`SearchHit.evidenceID`、`getEvidence(ids:)`、内部 `Set<Int64>` 去重）。
两台机器的 id 都从 1 开始，原样写入之后 `(A,7)` 与 `(B,7)` 在检索层就是同一个 Int64——
搜索去重会把两条不同的证据当成一条，`get_evidence` 会返回错的那一条。
要原样写，就得把 `Store+Search` / `+Evidence` / `+Query` / `+Ledger` 与 MCP 协议的 id
全部改成复合键；而这几个文件正是本批并行任务（T11 向量检索、T14 周台账）在改的，
硬约束 10 要求共享文件只做追加式改动。

换成本机 id 空间之后：

- 检索层**一行都没改**，入站记录自动被 `search` / `get_evidence` / `get_item` / `get_context`
  查得到（本任务的验收要求，测试里逐条钉住）；
- 全局身份仍然唯一，只是它叫 `(origin_device, origin_id)`，写在列上而不是主键里；
- 出站只发 `origin_device IS NULL` 的行（本机自己产生的），**不会把别人的记录转发回去**，
  两台机器之间不会来回打转（测试 `testTombstonePropagation` 断言 `pendingTombstones == 0`）；
- 墓碑用 `(origin_device, origin_id)` 指目标，对端能精确定位到自己的那一份副本。

**代价**：同一条记录在两台机器上的**本机 id 不同**。要跨机器指同一条记录，用 origin 两列
（`Store.syncOrigin(observationID:)` / `syncLocalObservationID(originDevice:originID:)`）。

### 1.4 会话与台账只用本机观察

`Store+Sessions` 的三条取数加了 `origin_device IS NULL`。理由：3.7 的 `dwell_s` / `active_s` /
`unknown_s` 是"这台机器的屏幕时间"；把另一台机器的观察混进同一条时间线，会造出根本没发生过的
应用切换，并把同一段墙钟时间记两遍。`sessions` / `ledgers` 本来就是**派生结果、不同步**
（3.9 只列了四类不可变记录）。入站**墓碑**仍然会让本机的 sessions / ledgers 标 `stale`（3.8 的级联）。
跨设备合并台账不在本任务范围（见 §7）。

### 1.5 段文件与密钥

段文件：`magic "BRSSEG" + 版本 + UInt32 段头长度 + 明文段头 JSON + AES-GCM combined`。
明文是 JSON Lines（`h` 头 / `t` 正文 / `o` 观察含 occurrence / `d` 墓碑）。三层校验各管一件事：

| 校验 | 覆盖什么 | 报什么 |
|---|---|---|
| 段头里的密文 SHA-256 | 文件本身坏了（传输截断、同步盘写坏） | `checksumMismatch` |
| GCM tag（AAD = 去掉 checksum 的段头骨架） | 密钥不对，**或段头被改过**（改名 / 改 seq / 改 device） | `decryptFailed` |
| `plainBytes` 与三个计数 | 明文与段头声明不一致 | `corruptSegment` |

**段是自包含的**：段里引用某个 sha 就带上它的正文，哪怕更早的段发过。代价是跨段重复
（实测 +5.1%，见 §3），换来两件事：任何一个段都能独立导入；对端把那条正文删掉之后
（3.8 的孤儿清理），后面的段也不会永远解析不了。段内按 sha 去重。

**不引入压缩**：本轮不引第三方依赖，系统里没有 zstd；段文件是用完即删的传输载体
（两边都 ack 就清理），先把正确性做对。

密钥三把分开：库密钥（钥匙串，开库）、同步密钥（256 位随机，**存在加密库里**，只封段文件）、
配对口令（24 字符 / 120 bit，**哪都不存**，首台显示一次）。
同步密钥放库里而不是再要一个钥匙串条目：钥匙串写入会弹授权框（本轮不允许触发）；库本身已经是
SQLCipher 加密的；只有一个持钥者。代价是拿到库密钥的人也拿得到同步密钥——但拿到库密钥本来就能
读全部原文，同步密钥保护的是它的**子集**，边界没有降低。

包裹参数：PBKDF2-HMAC-SHA256 × **600,000**（OWASP 2023 对该算法的建议值）、每份包裹自己的
16 字节随机盐、输出 32 字节 → HKDF-SHA256（info `brosis-sync/1 keywrap`）域分离 → AES-256-GCM，
AAD 绑 `brosis-sync/1|wrap|<device_id>`。不用 Argon2id：本轮不引第三方依赖，
系统里只有 CommonCrypto 的 PBKDF2。

口令生成规则：字母表 32 个字符 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（去掉 `0/O`、`1/I/L`），
`SecRandomCopyBytes` 取 24 字节、每字节取模（`256 % 32 == 0`，无偏置），
6 组 × 4 字符 = **120 bit**，显示成 `ABCD-EFGH-…`。输入时大小写与分隔符都无所谓，
字母表外的字符直接判非法（不去做 60 万次 PBKDF2）。

## 2. 怎么跑

全部命令可直接复制。`$BIN` = `~/Library/Caches/brosis-build/m2-sync-core/debug/brosis-store`。

```bash
cd "<项目目录>"

# 1) core：构建 + 全量测试（零 warning、163 个用例）
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift build --package-path core --scratch-path "$HOME/Library/Caches/brosis-build/m2-sync-core"
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test  --package-path core --scratch-path "$HOME/Library/Caches/brosis-build/m2-sync-core"
# 只跑同步的 14 个用例：
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  swift test  --package-path core --scratch-path "$HOME/Library/Caches/brosis-build/m2-sync-core" \
  --filter SyncTests

# 2) app：构建 + 签名 + 自检（含两库往返冒烟）
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
  SCRATCH="$HOME/Library/Caches/brosis-build/m2-sync-app" bash app/build_app.sh

# 3) 命令行两库往返（不需要 GUI、不碰钥匙串）
BIN="$HOME/Library/Caches/brosis-build/m2-sync-core/debug/brosis-store"
W="$HOME/Library/Caches/brosis-build/m2-sync/demo"; rm -rf "$W"; mkdir -p "$W"
"$BIN" init --dir "$W/A" --key-file "$W/A.key" --device-id demo-A
"$BIN" init --dir "$W/B" --key-file "$W/B.key" --device-id demo-B
"$BIN" gen-jsonl --out "$W/a.jsonl" --count 40 --seed 11
"$BIN" import-jsonl --dir "$W/A" --key-file "$W/A.key" --file "$W/a.jsonl"
"$BIN" sync-init   --dir "$W/A" --key-file "$W/A.key" --sync-dir "$W/sync"   # 打印一次配对口令
"$BIN" sync-export --dir "$W/A" --key-file "$W/A.key" --sync-dir "$W/sync"
"$BIN" sync-import --dir "$W/B" --key-file "$W/B.key" --sync-dir "$W/sync" --passphrase "<上面那串>"
"$BIN" search      --dir "$W/B" --key-file "$W/B.key" --q "<A 库里的某段文字>"
"$BIN" sync-cleanup --dir "$W/A" --key-file "$W/A.key" --sync-dir "$W/sync"
```

（`gen.log`、`import.json` / `.time`、`db-stats.json`、`sync-export.json` / `.time`、
`sync-import.json` / `.time`、`sync5-export.json`、`base.time` / `create.time` / `join.time`）。

### 3.5 KDF 代价（M4 Air，PBKDF2-HMAC-SHA256 × 600,000）

| 操作 | 进程 real | 扣掉基线后的 KDF 时间 |
|---|---|---|
| `sync-status`（库里已有密钥，不做 KDF） | 0.01 s | — |
| `sync-init` 建目录（1 次包裹 = 1 次派生） | 0.09 s | ≈ **80 ms** |
| `sync-init` 加入（1 次解包 + 1 次包裹 = 2 次派生） | 0.18 s | ≈ **85 ms / 次** |

口径说明：M4 有 ARMv8 SHA-256 指令，600k 次 HMAC 只要 80 ms，比常见的 x86 数字快一个量级。
**真正的防护是口令本身的 120 bit 熵**（32 字母表 × 24 字符），PBKDF2 的迭代数是纵深防御；
口令只在"新设备加入"时用一次，80 ms 的交互代价可以忽略，所以没有为了"更慢"而调高迭代数
——那只会让加入变慢而对 120 bit 的口令毫无意义。

| 项 | 结果 |

> 检查退化成"对已经导过的段做无效篡改"。改成 A 先真的再记一条再导出，并加断言
> "对端 `imported_seq` 没有前进"，才是真的在测这件事。

## 6. app 侧：接入方式（`AppDelegate.swift` 一行没改）

三个新文件：`SyncController.swift`（开关 + 循环 + 状态 + 事件）、`SyncWindow.swift`（设置窗口）、
`SyncSelfCheck.swift`（自检里的两库往返冒烟）。`SelfCheck.swift` 只加了一行
`failures += SyncSelfCheck.run()`。

**主会话要加的两行 + 一个菜单项**：

```swift
// AppDelegate.applicationDidFinishLaunching(_:)，lock 建好之后：
sync = SyncController()
sync.install(lock: lock, recorder: recorder)

// 菜单（可选）：
menu.addItem(NSMenuItem(title: "跨设备同步…", action: #selector(openSync), keyEquivalent: ""))
@objc private func openSync() { sync?.presentWindow() }
```

`install` **链式保留** `LockController` 原有的 `onUnlocked` / `onLocking`（不覆盖），
所以加这两行不改变现有行为。

循环口径：只在 `phase == .unlocked` 跑；**`paused` 不停同步**（暂停的是采集新内容，
同步只搬运已经采集到的东西，不产生新观察、不看屏幕——这是一条判断，不是疏忽）；
默认 5 分钟一轮（`sync.intervalSeconds` 可改，下限 30 s）；文件 I/O 与加密全在一条 utility
串行队列上，一轮没跑完不会再起一轮。`SyncEngine` 标了 `@unchecked Sendable` 但**不是线程安全的**，
类注释写明"同一个实例的全部方法必须在同一条串行队列上调用"，`SyncController` 连状态刷新
也走同一条队列。

UserDefaults 键：`sync.enabled`（默认 false）、`sync.directory`（默认
`~/Library/Mobile Documents/com~apple~CloudDocs/brosis-sync`）、`sync.intervalSeconds`（300）、
`sync.deviceName`（默认电脑名，**只写进同步目录**，不入库）。

事件（写 `jobs` 的 `runtime_event:*`）：`sync_folder_created` / `sync_joined` / `sync_enabled` /
`sync_disabled` / `sync_round` / `sync_export` / `sync_import` / `sync_missing_segment` /
`sync_import_failed` / `sync_manifest_conflict` / `sync_cleanup` / `sync_open_failed`。
`sync_enabled` 只记目录**种类**（`icloud_drive` / `icloud_container` / `custom`），不记路径。

## 7. 未做与原因

1. **iCloud 钥匙串自动同步密钥**（3.9「若 E6 证实…再提供便利选项」）：没做。
   它要真人点钥匙串授权对话框，本轮屏幕锁定、用户不在场，硬约束禁止触发 TCC / 钥匙串弹窗。
   接口留在 `SyncEngine.openOrCreate` 的 `passphrase` 参数上：将来在"库里没有密钥"那条分支前
   加一次"从可同步钥匙串取"的尝试即可，口令仍作兜底。
2. **真机两台机器实测同步延迟**：没做，需要用户在两台真机上跑（见 §8）。
   本轮全部用本地临时目录模拟，`ensureDownloaded` 的 **iCloud 分支没有被执行到**
   （非 iCloud 目录走的是"文件已在"的早退分支）。
3. **跨设备合并台账 / 会话**：没做，理由见 §1.4（合并会造假的应用切换并重复计时）。
   要做的话方向是"按来源设备分组各建一套会话"，需要给 `sessions` 加来源列，是另一个任务。
4. **段文件压缩**：没做。本轮不引第三方依赖（系统无 zstd）；Apple 的 `Compression` 框架可用，
   但会在段格式上加一层要长期兼容的东西，而段是用完即删的传输载体。
   实测中文正文在 JSON 里不转义，压缩收益主要来自重复的字段名与 URL——留给需要时再评估。
5. **"退出并删除本机段文件"**（3.9 提到的独立操作）：没做，界面上也没有入口。
   关开关只停循环、保留本机已合并的数据（这一半做了）。
6. **每 N 条触发出站**（3.9「每 5 分钟或每 N 条」）：只做了定时那一半。
   条数触发要在采集热路径上加计数与回调，收益不大（5 分钟已经够密），留到真机试用后再看。
7. **配额过期与入站记录的关系**：`expire()`（3.8 的配额，本机策略）按时间从旧到新**物理删行**，
   不区分是本机产生的还是导入来的。这是有意的——配额是本机策略，另一台机器可以设不一样的配额，
   而且被删掉的那份在源机器上还在。副作用：本机 `origin` 索引里那条映射也没了，
   如果同一个段将来又被重放（只可能发生在"删掉本机同步状态重新加入"的场景），
   那条记录会被重新导入一次。这与 3.8 的"配额不同步"是同一件事的两面，没有额外处理。
8. **段文件的并发出站**：`exportOnce` 一次最多写 8 个段（`maxSegmentsPerRun`），
   第一次同步一个 1 个月的库要跑 17 轮才发完（130 段）。是有意的：不让第一次同步把
   一条队列占死。命令行可以 `--max-segments 500` 一次发完（§3.3 就是这么测的）。

## 8. 需要你在两台真机上做的

1. 在**一台**机器上打开开关 → 记下它显示的**一次性配对口令**（关掉就再也看不到了）；
   确认 iCloud Drive 里出现 `brosis-sync/` 且里面有 `manifest.json` / `keyring/` / `devices/`。
2. 在**另一台**机器上打开开关、输入口令 → 确认它出现在第一台的"其他设备"列表里。
3. 两台机器各记录一段内容，等 5–10 分钟，确认互相都能 `search` 到对方的内容并展开原文；
   **记一下实际延迟**（这就是 4.3 说的"用两台机器实测同步延迟"）。
4. 在一台上删除一段内容，确认另一台在下一轮同步后 `search` / `get_evidence` 都不再返回。
5. 让其中一台离线几天，回来后确认段文件是否被 iCloud 驱逐成占位符（`ls -a` 看
   `.000000000012.seg.icloud`），以及导入时是否能自动下载并继续——**这条只有真机能验**。
6. 故意在两台机器上"几乎同时"第一次打开开关，看是否出现两个 manifest 并被提示停止。
7. 观察 `brosis-sync/` 的体积增长是否与 §3.3 的 10.1 MiB/天量级一致，以及 ack 清理是否在两台
   都导完之后把老段删掉。
