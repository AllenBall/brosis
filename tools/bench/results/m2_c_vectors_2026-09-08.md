### 1.1 「core 的新库目标」还是「app 内模块」：**选了 app 内模块**

任务给了二选一。选 **app 包里的 `BrosisModels` 目标**，理由三条：

1. **core 要保持零 mlx 依赖**。放进 core 的话，`swift test --package-path core` 每次都要先解析、
   编译 mlx-swift（几分钟 + 数 GiB），验收者「从零重建」的代价会翻好几倍；
   而 core 的 166 个用例一条都用不到模型。
2. **`brosis-mcp` 不能被拖胖**。它现在 1 MiB 出头、只链 `BrosisIPC`，
   「编译期就保证它拿不到 Store、拿不到密钥」这条设计不能因为加个模型库而松动。
3. **计划 3.10 的抽象本来就在 core**。core 只留 `EmbeddingProvider` 协议
   （`embed(texts)`），本地 mlx 实现放 app、由 app 注入。线上适配器**按用户本轮指示不写**。

代价：`brosis-store` 自己不能用真实模型跑嵌入（只带确定性伪嵌入 `--provider hash`）。
真实模型那条路走 `brosis-embed`，**检索仍然走 `brosis-store search-batch`**，
所以 D8 量到的是产品行为，不是另写一套。

## 2. schema v4 与检索层

### 2.1 两张表

```sql
CREATE TABLE chunks (
  vrow INTEGER PRIMARY KEY, device_id TEXT NOT NULL, text_version_id INTEGER NOT NULL,
  ord INTEGER NOT NULL, "offset" INTEGER NOT NULL, len INTEGER NOT NULL, chars INTEGER NOT NULL,
  embedded_at INTEGER, model TEXT, dim INTEGER,
  UNIQUE (device_id, text_version_id, ord),
  FOREIGN KEY (device_id, text_version_id) REFERENCES text_versions(device_id, id) ON DELETE CASCADE);
CREATE VIRTUAL TABLE vec_chunks USING vec0(
  chunk_rowid INTEGER PRIMARY KEY, embedding int8[512] distance_metric=cosine);
```

`offset` / `len` 是**原文 UTF-8 字节**偏移与长度，与 `text_versions.byte_len` 同口径；不复制正文。
两张表都是**本机派生数据**（同 `text_fts`）：删了能重建、不参与 D17 同步、不是证据。

**迁移版本按分配用了 v4**；T13 的同步是 v5，两边在 `Store.migrateIfNeeded` 里各占一个 `if found < N` 块，
互不干扰（本轮结束时磁盘上 `Schema.version == 5`，`migrations` 表里 1…5 各一行）。
v4 的审计行用 `ON CONFLICT(version) DO UPDATE` 写，所以迁移能被中断后重跑。

### 2.2 为什么是 512 维、int8、cosine

| 选择 | 依据 |
|---|---|
| **512 维** | E9 实测 MRL 截断：Qwen3-Embedding-0.6B 原生 1024 维，截到 **512 维 Recall@10 = 0.925**、256 维 0.90（`e9_runtime_2026-09-07.md`、报告 11.2 第 7 条）。512 在几乎不掉保真的前提下把向量体积减半。截断口径 = 取前 512 维再重新 L2 归一化 |
| **int8** | 512 维 float32 = 2 KiB/块、int8 = 512 B/块。本轮实测索引 46,545 块占 **24.55 MiB**（见 4.3），换 float32 就是 98.19 MiB，直接影响 D21 的 0.6 GiB/月目标。sqlite-vec v0.1.9 只有 float32 / int8 / bit，**没有 float16** |
| **cosine** | `vec0` 的 `distance_cosine_int8` = `1 - dot/(|a||b|)`，**对整体缩放不敏感**，所以每条向量能各自用 `s = 127 / max|v_i|` 缩放到满量程再取整。固定乘 127 会很糟：L2 归一化的 512 维向量分量典型只有 ±0.04，乘完只剩十来个量化档 |

量化误差实测（`VectorTests.testInt8QuantizationPreservesCosineOrder`）：
按条缩放后的 int8 余弦与精确余弦差 **< 0.01**。

**踩到的坑**：SQLite 的 subtype **不跨子查询传播**。
`INSERT INTO vec_chunks SELECT vec_int8(embedding) FROM vec_chunks` 报
`expected int8, but float32 was provided`；产品路径写的是 `VALUES (?, vec_int8(?))`。

### 2.3 分块策略

先按**段落**（换行为界）切，再按目标长度攒（`targetCharacters` 500，攒到再加一段就超过为止），
单段超过 `maxCharacters`（700）时按**固定字符窗**切开、窗间留 `overlapCharacters`（80）字符重叠，
丢掉纯空白与 `< 8` 字符的块，每个版本最多 64 块。
段与段之间补回被吃掉的 `\n`，所以按 `offset` / `len` 取回来与原文**逐字节相同**。
没有随机数（`testChunkerIsDeterministic` / `testChunkerSliceRoundTrip` 钉这两条）。

本轮语料实测：**28,588 个文本版本 → 46,545 块**（1.63 块/版本）。
语料的平均正文长度 538 字符（`gen_synth.json` 的 `avg_chars_per_text`）、汉字占 31.5%、1.66 字节/字符，所以大多数版本切成 1–2 块。
满档语料（`avg-chars 1500`）：**84,746 个版本 → 310,411 块**（3.66 块/版本）。

### 2.4 混合检索：加权 RRF

```
score(d) = Σ_c  w_c / (k + rank_c(d))      k = rrfK = 60
w = 1.0（精确字段 / 1–2 字扫描 / FTS）    w = 0.5（向量，vectorWeight）
```

* **为什么是 RRF 不是分数加权**：四条通道的分数没有可比量纲——精确字段通道没有分数、
  FTS 这里不用 bm25（E7 §10.2 换成 rowid 倒序）、向量给的是余弦距离。RRF 只用名次。
* **为什么向量权重减半**：前三条是精确子串语义，命中即真命中。
  精确命中拿 `1.0/61 = 0.01639`，向量第一名拿 `0.5/61 = 0.00820`，所以精确命中赢。
  `testVectorWeightCannotOutrankExactHit` 用「15 条向量距离为 0 的干扰项 + 1 条 FTS 精确命中」
  钉住这条；把权重改成 20 这条用例立刻失败（见第 8 节变异检验）。
* **向量关着时走老口径**（`fusion == "union"`），与 v3 逐位相同。

三道门（顺序有意义，**开关关着时连一次 `COUNT` 都不查**）：
`disabled`（默认）→ `no_query_vector`（调用方没给向量）→ `no_index`（库里没有向量）。
任一命中就 `vectorsUnavailable = true`，前三条通道完全不受影响——这就是 3.11 降级表里那一行。

**逐条命中的距离交给调用方**：`SearchHit.vectorDistance`。语义是「向量通道也找到了它，
距离是这么多」，与 `channel` 标了哪条无关。理由见第 5.4 节：
单一距离阈值分不开「库里没有这个内容」与「换了个说法的真命中」，所以这一层如实交出距离，
由 MCP 客户端 / Agent 决定要不要展开成证据。

### 2.5 一致性与夜间对账

`integrityReport()` 从 13 项加到 **16 项**，新增三项：
「chunk 指向不存在的 text_version」「向量行没有对应的 chunk」「标了已嵌入却没有向量行的 chunk」。
`maintenance()` 相应多做两件事：删孤儿向量行、把「标了已嵌入却没有向量行」的块改回待办。

**删除级联**：`chunks` 靠外键 `ON DELETE CASCADE` 跟着 `text_versions` 走；
`vec_chunks` 是虚拟表、**外键管不到**，由 `sweepOrphanVersions` 在删版本**之前**取出块 vrow 显式删。
用户删除与配额过期两条路都覆盖（`testKNNRoundTripAndDeleteCascade` / `testExpireAlsoDropsVectors`）。

**清单项 `files` 为空时导入必须拒绝**（自检里那一项就是拿置灰的 gemma 项试的）。

### 4.5 夜间任务门控与预算

九条判定全在 `EmbeddingGatePolicy.decide`（纯函数），自检跑 **14 条用例**：
接电、空闲 **≥ 5 分钟**（299 s vs 300 s 边界）、`thermalState == nominal`（fair / serious 都暂停）、
库未锁、未暂停、模型已装、开关已开、有待办、日均 GPU 预算未用完。
预算默认 **600 s = 10 分钟**（4.3 验收「日均 GPU < 10 分钟」），存 UserDefaults、跨日归零，
每次运行往 `jobs` 写一行 `runtime_event:embedding_run`，
`input_ref` 带块数 / 剩余 / GPU 秒数 / **今日累计** / 预算 / 停止原因 / 峰值 footprint / 热状态。

**按本轮实测折算日均 GPU**：整轮建索引 40,225 块 / 5,515 provider 秒 = **7.29 块/s**
（全程 `thermalState = fair`），10 分钟预算 ≈ **4,374 块/天**。
本轮语料 46,545 块要 **10.6 天**建完；满档语料 310,411 块要 **71 天**。
这条是给 4.3「日均 GPU < 10 分钟」的现实注脚：**Air 上首次全量建索引需要按周计**，
增量（每天新增的观察）才是 10 分钟预算能覆盖的量级。主会话可考虑把首次建索引
做成"用户显式确认后连续跑一晚"的一次性动作。

## 5. D8 裁决数据

### 5.1 实验怎么设计的

D8 的门槛原文：「Recall@10 提升 ≥ 5 个百分点**或解决明确的高价值失败**才纳入」。
这次给的是后者的数据，外加前者的对照。

**「明确的高价值失败」= 改写题**：同一个问题换一种说法，标准答案与原题相同。
本项目的 FTS 通道是「bigram phrase 命中 → 在**原文**上做子串复核」（D22 + 3.4），
语义上等于**精确子串**；换说法之后原文里没有那个子串，FTS 必然一条都召不回。
所以这套题量的正是「向量到底解决了什么 FTS 解决不了的问题」。

`tools/eval/make_paraphrase_queryset.py` 从 60 题里**真值是正文**的 35 道派生出
**47 道**改写题（同义改写 18、术语换说法 15、中英互译 14），生成时逐条断言：
标准答案与原题相同、**改写串里不能含原词**、真值非空、总数 ≥ 40；没有随机数，两次生成逐字节相同。

**为什么不从 `app:` / `host:` / `path:` 那几类派生**：那几题的真值是"这个应用 / 站点的全部观察"，
把「飞书」换成「Lark 这个协作软件」属于 Agent 该不该做 bundle id 映射的问题，
不是检索层的问题；混进来只会让两条通道一起掉分，量不出东西。

**两个跑法用同一条产品检索路径**（`brosis-store search-batch`），差别只有开关：
FTS-only 不带 `--vectors`，混合带 `--vectors --query-vectors <向量表>`。
查询向量由 `brosis-embed queries` 用**真实模型** Qwen3-Embedding-0.6B-8bit 事先算好；
改写题的 `search.q` 与 `embed_text` **完全一样**，两条通道量的是同一个查询。

### 5.2 改写题：FTS-only vs 混合检索

| 指标（47 道改写题，全部可答） | FTS-only | 混合检索 | 差 |
|---|---:|---:|---:|
| **Recall@10** | 0.0000 | **0.2774** | **+27.74 个百分点** |
| **MRR@10** | 0.0000 | **0.6619** | +0.6619 |
| Precision@10 | 0.0000 | 0.4515 | +0.4515 |
| **至少答出一条真证据的题数** | **0 / 47** | **32 / 47** | +32 |
| 单题热延迟 p50 / p95 | 0.10 / 0.17 ms | 22.17 / 56.20 ms | — |

按改写类别（混合检索）：

| 改写类别 | 题数 | Recall@10 | MRR@10 |
|---|---:|---:|---:|
| 同义改写 | 18 | 0.2554 | 0.6111 |
| 术语换说法 | 15 | 0.2699 | 0.7407 |
| 中英互译 | 14 | 0.3137 | 0.6429 |

**FTS-only 在这套题上是 0**，不是「低」，是**一条都召不回**——这正是设计这套题要证明的：换一种说法之后，精确子串语义的通道没有任何机会。

被向量救回来的题：**32 道**；被向量挤下去的题：**0 道**。

### 5.3 原 60 题：不退化

| 指标（60 题：50 道可答 + 10 道不可答） | FTS-only | 混合检索 | 差 |
|---|---:|---:|---:|
| Recall@10（可答题） | 1.0000 | 1.0000 | +0.00 个百分点 |
| MRR@10（可答题） | 1.0000 | 1.0000 | +0.0000 |
| Precision@10（可答题） | 1.0000 | 0.9780 | -0.0220 |
| **负例误报**（10 道不可答题里返回了证据的） | **0** | **2** | +2 |
| 被挤下去的题 | — | **0** | — |
| 单题热延迟 p50 / p95 | 1.29 / 13.11 ms | 21.77 / 60.99 ms | — |

**不退化**：可答题的 Recall@10 与 MRR@10 **一个数没变**，也没有任何一道题的召回被向量挤低。
这就是加权 RRF 里 `vectorWeight = 0.5` 要保证的事（第 2.4 节）。

两处要说清楚的细节：

1. **Precision@10 掉的 0.022 不是丢证据**。掉分的是 `cross-03` / `det-16` / `det-17` / `det-18`
   四道题，它们的真值分别只有 7 / 9 / 7 / 6 条；FTS-only 只返回那几条（按
   `|命中| / min(10, 返回条数)` 算就是 1.0），混合把剩下的空位用向量候选填满 10 条，
   分母变成 10，分子没变。**四道题的 Recall@10 都仍然是 1.000。**
   换句话说：这是"多给了几条相关度中等的候选"，不是"挤掉了真证据"。
2. **2 条负例误报都是"生僻外来词"那一类**：`del-02`（已删除的 `zygomorphic`，最好距离 0.3819）
   与 `none-04`（`flibbertigibbet`，0.3253）。两条都**只有向量通道**返回，
   距离也明显比可答题的典型值（0.09–0.26）差。也就是说：
   信号是在的（`SearchHit.vectorDistance` 已经把它交出去了），
   只是一个**全局**阈值没法把它和"换了说法的真命中"分开——见 5.4。

### 5.4 向量距离阈值扫描：`vectorMaxDistance` 该取多少

向量通道给的是**最近邻**，「库里根本没有这个内容」的查询照样能拿到一堆相似度不高的块；
而 `docs/查询集草稿.md` 规定不可答题「编造一次即失败」。这一节量的就是这个取舍。

| `vectorMaxDistance` | 改写题 Recall@10 | 改写题 MRR@10 | 改写题答出 | 原 60 题 Recall@10 | **负例误报** |
|---:|---:|---:|---:|---:|---:|
| 0.30 | 0.0480 | 0.2553 | 12 / 47 | 1.0000 | 0 |
| 0.35 | 0.1491 | 0.5343 | 26 / 47 | 1.0000 | 1 |
| **0.40** | **0.2774** | 0.6619 | **32 / 47** | 1.0000 | **2** |
| 0.45 | 0.3416 | 0.7683 | 37 / 47 | 1.0000 | 2 |
| 0.50 | 0.3846 | 0.7967 | 39 / 47 | 1.0000 | 4 |
| 0.55 | 0.4053 | 0.7967 | 39 / 47 | 1.0000 | 6 |
| 0.60 | 0.4053 | 0.7967 | 39 / 47 | 1.0000 | 6 |
| 不设闸 | 0.4074 | 0.7967 | 39 / 47 | 1.0000 | 6 |
| （FTS-only 基线） | 0.0000 | 0.0000 | 0 / 47 | 1.0000 | 0 |

两条曲线朝相反方向走：闸门放松，改写题召回涨、负例误报也涨。

**默认取 0.40**（本轮已把 `RetrievalOptions.vectorMaxDistance` 从初版的 0.6 改成它）。
在同样是 2 条负例误报的 0.40 与 0.45 之间选**更紧的那个**：
不可答题只有 10 道，「2 vs 2」很可能是噪声，而误报的伤害是不对称的
（一次编造就毁掉整个工具的可信度）。想要更高召回的人有明确的下一步：
调到 0.45 能多救回 5 道题、本轮实测误报不变。

**必须写清楚的第二个发现：这个阈值不随索引规模自适应。**
同一套题、同一个阈值，索引建到不同程度时负例误报是：

| 索引建成度 | 阈值 0.35 的误报 | 阈值 0.40 的误报 | 0.40 时改写题 Recall@10 / 答出 |
|---:|---:|---:|---:|
| 37%（17.2k / 46.5k 块） | 0 | **0** | 0.1325 / 26 题 |
| 66%（30.7k / 46.5k 块） | 1 | **2** | 0.2008 / 30 题 |
| **100%（46.5k 块）** | 1 | **2** | **0.2774 / 32 题** |

块越多，「库里没有的内容」的最近邻也越近，所以**同一个阈值会随着索引变大而漏进更多误报**。
0.40 因此不是一劳永逸的分界线，而是**要随语料规模复核的常量**；12 个月库上必须重跑这张表。

**更关键的是：这份数据里根本不存在「零编造 + 有用召回」的阈值。**
零编造要收到 0.30，那里只救回 12 / 47 题（Recall@10 0.048）；
把召回做到 32 / 47 就要接受 10 道不可答题里有 2 道返回（弱）证据。
真正的解法不在这一层——`SearchHit.vectorDistance` 已经把逐条距离交给调用方，
让上层按「这是精确命中还是相似」自己决定要不要展开成证据。见第 6 节的条件 2。

### 5.5 延迟

同一台机器、同一个库上，两个跑法的单题热延迟（`search-batch` 逐题计时）：

| 题集 | FTS-only p50 / p95 | 混合 p50 / p95 |
|---|---:|---:|
| 原 60 题 | 1.29 / 13.11 ms | 21.77 / 60.99 ms |
| 改写题 47 道 | 0.10 / 0.17 ms | 22.17 / 56.20 ms |

**纯向量 kNN 单独量**（每次一个新进程，页缓存冷，含 SQLCipher 逐页解密）：

| 向量行数 | 5 次的中位 |
|---:|---:|
| 28,016（索引 60%） | 30.25 ms |
| **46,545（建完）** | **42.93 ms**（42.43 / 42.75 / 42.93 / 43.45 / 43.48） |

1.66 倍的向量数只涨了 1.42 倍时间——差额是每次都要付的进程启动与开库成本，
所以**产品路径（常驻进程、页缓存已热）看的是上面那张表的 p50 ≈ 22 ms**。

**sqlite-vec v0.1.9 的 kNN 是全量扫描**（没有 ANN 索引），所以它随块数线性：
满档 1 个月语料 310,411 块要按 **6.7 倍**折算（热 p50 约 150 ms），12 个月库还要再乘 12（约 1.8 s）。
**计划 3.4 的「热 p95 < 10 ms」只约束 FTS 与精确字段通道**，向量通道要单独定一个目标；
按本轮实测建议定为「**1 个月库热 p95 ≤ 100 ms**」，并记下一条：
**12 个月库上全量扫描不可接受，到那时必须换 ANN 索引或按时间窗分片**。

## 6. D8 建议：**有条件通过**

**建议纳入向量检索，但带三个条件。**

**通过的依据**（第 5.2 节）：47 道改写题上，现在的系统（精确字段 + 扫描 + FTS）
**一道都答不出**（Recall@10 = 0、MRR = 0、答出 0 / 47）；加上向量之后
**32 / 47 道能答出至少一条真证据**（Recall@10 0.2774、MRR@10 0.6619）。
这是 D8 说的「解决明确的高价值失败」——**不是排序变好，是从"完全没有"变成"有"**。
对一个「你上周说的那件事」的记忆工具来说，用户不会每次都用当初屏幕上的原词提问，
这一类失败正是真实使用里最常见的。

**Recall@10 的绝对值（0.2774）要看清楚口径**：改写题的真值中位数是 13 条观察，
`Recall@10 = |前 10 ∩ 真值| / min(10, |真值|)` 的分母就是 10，
也就是要求前 10 条**全是**真值才算 1.0。
实际拿到的是：32 / 47 道能拿到真证据，**MRR@10 0.6619**——
第一条真证据平均排在第 1.5 位，Precision@10 0.4515（前 10 条里近一半是真值）。
对"拿到证据再展开原文"的用法这已经够用，但离"前 10 条都对"还很远。
**别把 0.2774 当成"向量检索的召回率"**：它是在一套刻意为难 FTS 的题上、
按最严口径算出来的**下界**。

**三个条件**：

1. **默认关，模型装了才可开**（本轮已经这么做）。没装模型时向量检索显示「未启用」，
   精确字段与 FTS 一点不受影响，这是 3.11 降级表的原文。
2. **距离闸不能松，而且要随语料规模复核**。`vectorMaxDistance` 默认 0.40。
   第 5.4 节的发现是：**同一个阈值会随索引变大而漏进更多负例误报**
   （索引 37% 时 0 条、66% 时 2 条）。所以这不是一个定死的常量：
   12 个月库上线之前必须重跑一次那张表。
   与之配套，`SearchHit.vectorDistance` 已经把**逐条距离**交给调用方
   （并且会随 MCP 的 `search` 一起返回），让 Agent 能区分「精确命中」与「相似」——
   长期看，**把"这条到底算不算证据"的判断交给调用方，比在存储层定一个全局阈值更稳**。
3. **首次全量建索引要按周计，不能塞进 10 分钟的日均预算**。
   本轮建完整索引**实测 1 小时 32 分**（40,225 块、7.29 块/s、全程 `thermalState = fair`）。
   按 10 分钟/天的预算折算 ≈ 4,374 块/天：本轮 46,545 块要 **10.6 天**，
   满档 1 个月语料 310,411 块要 **71 天**。
   建议把"首次建索引"做成用户显式确认后连续跑一晚的一次性动作，日均预算只管增量。

**如果你不接受第 3 条**（不想为首次索引付一晚 GPU），那 D8 应当判**不通过**——
增量索引解决不了"过去 30 天的内容查不到"这个问题，功能会长期处于半可用状态。

切出 310,411 块。按冷机探针的 11.41 块/s 是 7.6 小时；按本轮**整轮实测**的

**两条通道跑的是同一个库、同一套题**，所以比较成立；但绝对值比满档乐观
（干扰项少约 3 倍）。要在满档语料上复跑：`PER_DAY=8640 AVG_CHARS=1500 sh tools/eval/run_d8.sh`，
预留一整夜。

## 9. 未做与原因

1. **MCP 的 `search` 工具还没有向量通道**。`StoreMCPService.search` 调的是
   `store.search(q:…)`，没有查询向量，所以经 `brosis-mcp` 过来的查询一律
   `vectorsUnavailable = no_query_vector`。要接上得让 **app 侧的 IPC 服务端**
   在收到 `search` 时算查询向量（app 链接了 `BrosisModels`，core 不能算）。
   没做的原因是它牵扯**守护进程里的模型生命周期**：常驻会多占约 1.2 GiB，
   按需加载会给每次 MCP 查询加 0.4 s 冷启动，两条都要真机试过才好定；
   而本轮屏幕锁定、不能起 GUI，验证不了。
   建议的做法：`StoreMCPService` 上挂一个 `queryVectorProvider: ((String) -> [Float]?)?` 钩子，
   app 在「模型已装 + `vectorsEnabled` 开着」时注入一个带空闲卸载的懒加载 provider。
2. **满档 1 个月语料上的 D8 数字**。见第 7 节：7.6 小时，一次会话跑不完。
   脚本支持 `PER_DAY=8640 AVG_CHARS=1500`，留给一整夜。
3. **真实查询题（D12）上的 D8 数字**。本轮全部是合成题；合成语料的词是种进去的、
   真值是算出来的，只能证明方法与流程成立。
4. **模型下载没跑过**（硬约束「不下载未批准的模型」）。下载器代码逐字来自 E9 实测过的那份
   （直连 12.3 MiB/s、镜像续传 HTTP 206），本轮只走本地导入 + 重新校验 sha256。
5. **「模型」面板没有真机点过**。屏幕锁定、不起 GUI；面板的**判定逻辑**
   （清单读取、置灰原因、门控、预算台账、向量往返）全在 `--self-check` 里跑，
   画界面那部分只保证编译与签名后能加载。
6. **`Qwen3.5-4B-MLX-4bit` 本轮没加载过**。它在清单里、体积与最低内存都核对了，
   加载与生成属于 T12。
7. **sqlite-vec v0.1.9 的 kNN 是全量扫描**（没有 ANN 索引），延迟随块数线性。
   见第 5.5 节的实测；满档语料要按 6.7 倍折算。真要上 ANN 得换库或等上游。
8. **`brosis-embed` 占 app 体积 40.23 MiB**。它是评估 / 验收工具不是产品必需，
   主会话可决定是否从 bundle 里拿掉（见第 4.4 节）。
9. **`chunks` 表每行存了一遍 36 字节的 `device_id`**（UUID 字符串），
   表里一份、`UNIQUE (device_id, text_version_id, ord)` 索引里一份。
   本轮 46,545 块因此多花约 3.2 MiB。换成一张 `devices(id INTEGER, uuid TEXT)` 小表、
   `chunks` 只存整数设备号即可省掉，但那要动 schema、与 T13 的 v5 撞版本，
   而且省下的量在 1 个月库上只有几 MiB，**留给主会话按整体 schema 规划一起做**。
10. `SearchHit.vectorDistance` **已经会随 MCP 的 `search` 返回**（`StoreMCPService`
   直接把 `SearchResult` 与 `[SearchHit]` 编码出去，新字段自动带上），
   但因为第 1 条还没做，经 MCP 过来的查询目前一律 `vectorsUnavailable = no_query_vector`，
   所以那个字段现在总是 nil。**接上向量通道的同一次改动会让它自然生效，不用再改协议。**
11. **按查询自适应的距离阈值没做**。第 5.4 节量到固定阈值会随索引变大而漏进更多负例误报，
   本轮的处理只是「把 0.40 定成默认值 + 把逐条距离交出去 + 写明要随规模复核」。
   想真正解决要么按查询估一个"背景距离"再看命中比它好多少，要么让调用方自己判；
   两条都需要真实题（D12）上的数据才好定，本轮没有。
12. **`vec-search` 的冷 / 热延迟没有分开报**。第 5.5 节给的是 `search-batch` 里的热延迟
   （一个进程连跑，页缓存已热）；单独起进程跑一次 `vec-search` 实测 30 ms 上下
   （28k 向量，含 SQLCipher 逐页解密 14 MiB）。产品路径是常驻进程，热延迟才是它该看的数，
   但"开机后第一次向量查询要多久"这条没有系统量过。
