## 1. 做了什么

### 1.1 架构（按计划 3.1 / 3.6，没有让 MCP 进程直接开库）

```text
Claude Code 等 MCP 客户端
      │ stdio：换行分隔的 JSON-RPC 2.0
      ▼
brosis-mcp                       core 的新可执行产品，**只链接 BrosisIPC**
      │                          （编译期就拿不到 Store / SQLCipher / KeyProvider）
      │ Unix domain socket：<数据目录>/ipc.sock（0600），换行分隔 JSON
      ▼
brosis.app 的 MCPIPCService      挂在 LockController 上——本进程唯一持有 Store 的那一层
  └─ MCPGate（3.5 相位门）→ StoreMCPService（grant 判定 + 裁剪 + 审计）→ Store
```

`brosis-store serve` 是服务端的**测试替身**：同一个 `MCPGate` + `StoreMCPService` + `IPCServer`，
只是用 `FileKeyProvider` 开一个临时库，让 `swift test` 不启动 GUI 就能跑完整条链路。

### 1.3 六个工具与 grant 的关系（3.6）

没有 grant 的客户端**六个工具全拒**（`no_grant`），一个字节都不回。有 grant 时：

- **时间窗**（默认 30 天）是**硬下界**：客户端把 `start` 写到窗口之外也会被抬回来
  （结果里的 `appliedStart` 就是实际用的下界）；`get_context` 的 `hours` 被封顶并报
  `hoursClampedByGrant`；整段落在窗口外的 `get_timeline` / `get_day_ledger` 直接 `denied_by_grant`。
- **应用白名单**：`search` 内部多取 5 倍候选再过滤、截到 `limit`；`get_evidence` 的白名单外 id 进
  `deniedByGrant`，**它的出现上下文（`before` / `after`）也逐条按白名单与时间窗过滤**
  （相邻观察带 bundle id 与窗口标题；被丢掉的条数计进 `grant.droppedByGrant`，见 §9.1）；`get_item(app)` 白名单外直接拒；`get_timeline` 的每个桶按留下的应用**重算**
  dwell / active / unknown / 观察数 / 切换数；`get_day_ledger` 过滤 `apps` 并重算合计，
  `sites` / `files` / `onlineUnionS` / `perDisplayDwellS` / `sessions` / `interruptions` / `evidence`
  **整段丢掉**并列进 `droppedFields`（它们回不到"是哪个应用"，给近似值比不给更糟）。
- **字段级别**：`fields = summary`（默认）时 `get_evidence` 不回 `text`、不回逐片段正文，
  `redactedByGrant = true`；`get_context` 的每条片段截到 ≤ 100 token 并**按裁剪后的片段重拼 `text`**。
- `apps = ["*"]` 且 `fields = evidence` 时**什么都不裁**，返回值与 T3 的 API 完全一致。
- 每个结果都带一份 `grant` 块（客户端 / 模式 / 字段级别 / 白名单 / 时间窗 / 窗口起点 /
  是否裁过 / 裁掉几条），客户端不用猜自己拿到的是不是全量。

不符——数字与口径在第三轮改正（验收问题 §9.2），出处在本轮补齐。
带进程启动的那一行是 `latency.sh` 里
`/usr/bin/time -p python3 core/Tests/mcp_client.py …` 的 `real`（`PYTHONDONTWRITEBYTECODE=1`）。
服务端 `elapsedMS` 是**服务端自己计的**、从 `mcp_audit` 表读回来的，不是客户端估的。

检索本身的延迟口径是 T3 已经量过的（`m1_r1_retrieval_ledger_2026-09-07.md`），

1. **没有真的让 Claude Code 连上**。需要真人在终端跑 `claude mcp add` 并在 GUI 里点，

2. **`brosis.app` 运行时的 socket 没有实跑**。`MCPIPCService` 的生命周期挂在 `LockController`

3. **对端校验只到 Team ID 粒度**，而且本进程没有 Team ID（未签名 / ad-hoc 构建）时**一律拒绝**。

4. **严格本地模式没有强制手段**。`mode = strict_local` 只是 grants 表里的标记 + 审计；
   3.6 原话是"系统无法技术上验证客户端是否上传"。`admin grant list` 的输出里带着这句话。
5. **提示注入只做了分隔符 + `readOnlyHint` + 量的限制**，不是隔离（3.6 原话）。

7. **没有做 MCP 侧的压测**。检索延迟 T3 已经量过，T5 只在外面套了 IPC 与 JSON 编解码；

### 本轮踩到并修掉的两个坑（都写进了代码注释）

- **`umask` 是进程级的**：`IPCServer.start()` 为了让 socket 是 0600 先把 umask 收紧成 `0o177`，

### 9.1 【阻塞】应用白名单在 `get_evidence` 的相邻观察上失效

**问题**：`get_evidence` 返回的每条证据都带"出现上下文"——同一块屏上时间相邻的观察
（`items[].before` / `items[].after`），每条带 `appBundleID`、`windowTitle` 与摘要。
第一轮这两串**直接透传** `Store.getEvidence` 的结果，而 `Store.neighborRows` 不认识 grant，
于是 `apps = ["com.apple.Safari"]` 的客户端仍能看见 VSCode / 微信 / 终端 / 飞书的
bundle id 与窗口标题。白名单在 `search` / `get_context` / `get_item` / `get_day_ledger` /
`get_timeline` 五个入口都是对的，只有这一处漏。

**怎么修**：过滤放在 **core 的 `Store.neighborRows`**（`core/Sources/BrosisCore/Store+Evidence.swift`），
不是 MCP 那一层——这样**任何**带 grant 调 `getEvidence` 的调用方都拿不到白名单外的邻居，
而不是只堵住 MCP 这一条路。三件事：

1. `getEvidence` 把 `grant` 与算好的 `windowStart` 传给 `neighborRows`；
2. `neighborRows` 把时间窗压进 SQL（`AND o.ts >= ?`），并在取行时逐条 `grant.allows(app:)`；
   被丢掉的行**不占 `neighbors` 的名额**（白名单生效时内部多取 8 倍候选，封顶 200 行），
   所以"白名单内还有邻居"时不会因为前面几条被丢就少给；
3. 丢掉的条数进 `EvidenceResult.droppedNeighbors`（**只回条数不回 id**——回 id 本身就等于
   告诉调用方"这个时刻还有别的应用"），`StoreMCPService.runEvidence` 把它加进
   `grant.droppedByGrant`，审计的 `note` 里也多一段 `neighbors_dropped=N`。

## 10. 第三轮修复（第二轮验收在连接层挖出来的问题）

第二轮验收把功能面（grant 判定、裁剪、审计、闭环、变异检验）全部复核通过，
最后在**连接层**加了两个探针，挖出一个能把宿主进程打死的问题。本轮把它、以及顺藤摸到的
另外两个同源问题一起修了。

一句话概括这一节：**这个服务端跑在 `brosis.app` 进程里，所以「对面不按套路出牌」
绝不能变成「brosis 没了」。**

### 10.1 【阻塞】客户端发完请求就挂断 → 服务端被 SIGPIPE 打死

验收者的探针（连上、发一条请求、**不读响应直接 `close()`**）：

```text
polite  #0..#2: got 205 bytes, server alive=True    ← 老老实实读响应，没事
hang-up #0:     server alive=False rc=-13           ← 不读就挂断，服务端当场没
final rc -13                                        （-13 = 被 SIGPIPE 打死）
```

`brosis-store serve` 只是测试替身，**产品路径上这个服务端在 `brosis.app` 进程里**
（`LockController` 那一层持有 Store）。也就是说：任何一个 MCP 客户端只要在等结果时消失
（关窗口、Claude Code 重启、用户按取消、进程被 kill），brosis 的采集与锁定状态机就一起没了——
这是拒绝服务，不是"少回一次结果"。

回归用例 `IPCProtocolTests.testServerSurvivesPeerHangUpBeforeReadingResponse` 在修之前
把整个测试进程一起带走（`results/repro_sigpipe_before_fix.txt`）：

```text
error: Process '…/xctest -XCTest …testServerSurvivesPeerHangUpBeforeReadingResponse …'
       exited with unexpected signal code 13
EXIT=1
```

**修法**：`accept` 出来的每个 fd 都设 `SO_NOSIGPIPE`（`BrosisIPC` 新增
`IPCSocketOptions.suppressSIGPIPE(fd:)`）。写失败退化成 `EPIPE` **错误**，
服务端记一条 `ipc_write_error`、只掐这一条连接。选**每条 fd 的选项**而不是进程级的
`signal(SIGPIPE, SIG_IGN)`：`BrosisIPC` 是个库，不该顺手改掉宿主 app 别处的信号处置。

修后实测（`results/probe.log` §3，真的 `brosis-store serve` 进程）：

```text
挂断 #0 之后 serve 还活着 = True
挂断 #1 之后 serve 还活着 = True
挂断 #2 之后 serve 还活着 = True
  ipc_write_error 行数 = 3
  serve: ipc_write_error write 失败：errno 32（Broken pipe）
挂断之后照常服务：
  search isError=False brosis · search · client=claude-code …
```

用例里**必须看到 `ipc_write_error`** 才算数——否则可能只是时序上没撞到 `EPIPE`，
这条用例就什么都没验到。

### 10.2 【阻塞】服务端在会话中途没了又回来 → `brosis-mcp` 被 SIGPIPE 打死

同一个根因的另一侧，验收者的探针 B 复现：

```text
call#1 -> {"id":2,…,"result":{…}}                    ← 正常
server stopped; restarting
call#2 after restart -> NO RESPONSE (EOF/timeout)
brosis-mcp poll after call#2: -13                    ← 客户端进程也被 SIGPIPE 打死
```

**真实触发场景（第四轮改正，原文写错了）**：**`brosis.app` 退出 / 重启 / 崩溃**，
而 Claude Code 那一侧的 `brosis-mcp` 是长期挂着的。app 退出走
`LockController.shutdown()` → `MCPIPCService.stop()` → `IPCServer.stop()`，那里对每条**存活连接**
`shutdown(SHUT_RDWR)`（`core/Sources/BrosisIPC/IPCServer.swift:140`）、关监听、删 socket 文件；
崩溃 / 被杀则由内核收尾，对客户端是同一种断链。修之前，用户退一次 app（或它崩一次），
`brosis-mcp` 就死了，`/mcp` 里的 brosis 从此不响应，要重启 Claude Code 才能恢复。
app 重启是日常操作（改配置、升级、崩溃自动重开），所以严重度仍按【阻塞】记。

**原文错在哪、为什么要单列**：第三轮把这里写成"`brosis.app` 每锁一次就把 socket 摘掉、
解锁再挂回去，用户锁一次屏 MCP 就死了"。查代码不成立：`LockController.beginLock()`
（`app/Sources/brosis/LockController.swift:485-486`）只调 `ipc.detach()`，而
`MCPIPCService.detach()`（`app/Sources/brosis/IPCService.swift:107-111`）只把 `service` 置 `nil`
——**socket 与既有连接都保留**，锁定期间的调用拿到的是一条 `[locked]` 响应（3.5），不是断链；
`ipc.stop()` 只在 `shutdown()`（`LockController.swift:517`）里。`finishUnlock` 的
`ipc.startIfNeeded`（`:456`）在已经在跑时是 no-op，解锁不会重新 `bind`。
"socket 起来之后就不再关（除非退出）"本来就是 `IPCService.swift:15`、`app/README.md` 8.9、
`core/README.md`「3.5 的三种状态」三处白纸黑字写着的设计。
**修复本身（客户端 `SO_NOSIGPIPE` + 重连）对上面那个真实触发仍然正确且必要，代码一个字节没改，
改的只有这段动机文字**及它在 `core/README.md`、`app/README.md`、两处测试注释、
`IPCClient.swift` 两处注释里的复述。

**修法**：`IPCClient.connect()` 出来的 fd 同样设 `SO_NOSIGPIPE`。写已断连接变成 `EPIPE` 错误，
正好落进第二轮已经建好的那条路——"服务端肯定没执行过 → 重连再试一次"（§9.5）。

修后实测（`results/probe.log` §4：客户端停在第 2 次调用之前，把服务端整个停掉再起来）：

### 10.3 顺手挖出来的：`serve` 收到 SIGTERM 直接崩，收尾一行都没跑

修 10.2 的时候发现：`brosis-store serve` 收到 SIGTERM **不是干净退出，是崩**。

```text
kill -TERM → rc=133（= 128 + 5，SIGTRAP）
退出后 socket 文件还在吗：在
日志里没有 {"command":"serve","stopped":true}
```

崩溃报告（`~/Library/Logs/DiagnosticReports/brosis-store-*.ips`）指得很清楚：

```text
EXC_BREAKPOINT (SIGTRAP)
  libdispatch          _dispatch_assert_queue_fail
  libswift_Concurrency swift_task_isCurrentExecutorWithFlags…
  brosis-store         closure #31 in <main.swift 顶层>
  libdispatch          _dispatch_source_latch_and_call
```

**根因**：Swift 6 语言模式下 `main.swift` 的**顶层代码是 `@MainActor` 隔离的**，而
`DispatchSourceProtocol.setEventHandler(handler:)` 的参数**不是 `@Sendable`**——
于是顶层写出来的那个信号处理闭包跟着带上 MainActor 隔离检查；libdispatch 在自己的信号队列上
调它，`dispatch_assert_queue` 当场失败。同一个文件里 `asyncAfter` 的闭包没事，
因为它的参数是 `@Sendable`（所以 `--seconds` 到点的那条路一直是好的，只有信号这条路会崩）。

后果不只是"退出码难看"：`server.stop()` / `checkpoint()` / `close()` / 密钥清零**一行都没跑**，
socket 文件留在原地。下一次起服务的进程会看到一个"文件在、但没人监听"的死 socket，
客户端连上去拿到 `ECONNREFUSED`——本轮写重启用例时第一次就撞上了这个现象。

**修法**：把等信号那段挪进文件作用域的 `waitForShutdownSignal(seconds:)`。
文件作用域的函数默认 `nonisolated`，里面的闭包也就没有这个检查。
回归用例 `MCPEndToEndTests.testServeShutsDownCleanlyOnSIGTERM` 断言退出码 0、
`terminationReason == .exit`、socket 文件已删、日志里有 `"stopped" : true`。

**这个坑值得记在 `core/README.md` 里**（已记）：`main.swift` 顶层写的闭包，
只要交给非 `@Sendable` 的参数、又跑在别的队列上，就会踩。

### 10.4 顺手改的：重连之前先等 150 ms（**没有用例覆盖，如实说明**）

`IPCServer.start()` 里 `bind` 与 `listen` 之间有个极短的窗口，客户端恰好在这个窗口里
`connect` 会拿到 `ECONNREFUSED`。这个窗口只在服务端**起 socket** 时出现——
`brosis.app` 是启动后第一次解锁时起一次（之后锁定 / 解锁都不再 `bind`，见 §10.2），
`brosis-store serve` 是每次启动时。原来的重试是**立刻**重连（微秒级），等于没重试。
现在重试前 `usleep(150_000)`；服务端确实不在时，代价也只是慢 150 ms
（`testMCPReportsClearErrorWhenServerIsAbsent` 本轮实测 **0.337 s**，
出处 `m1-r2e-mcp/results/core_test.txt:117`；全新 scratch 那次是 0.339 s，
`clean_core_test.txt:186`。逐次抖动几毫秒：第三轮 0.336 / 0.331 s、第四轮 0.328 / 0.331 s，
所以这里看的是**量级**。报错文案不变）。

> 第四轮这一格写的 0.337 s 在当时保留的日志里找不到出处（验收问题，见 §12.4），
> 本轮重测后补上了行号。

**这一条没有回归用例**：那个窗口在测试里稳定复现不了（见 §10.5 的变异 m4——
把这行删掉，四个用例照样全绿）。它是纯保守改动，留着的理由写在代码注释里。

### 11.1 【主因】"锁定会摘掉 socket / 断连接"是错的

**验收者的证据链**（复核后完全成立）：

| 位置 | 实际行为 |
|---|---|
| `app/Sources/brosis/LockController.swift:485-486`（`beginLock()`） | 只调 `ipc.detach()` |
| `app/Sources/brosis/IPCService.swift:107-111`（`detach()`） | 只把 `service` 置 `nil`——**socket 与既有连接都保留** |
| `app/Sources/brosis/LockController.swift:517`（`shutdown()`） | 只有这里调 `ipc.stop()`，即**只有 app 退出**才关监听、断连接、删 socket |
| `app/Sources/brosis/LockController.swift:456`（`finishUnlock`） | `ipc.startIfNeeded` 在已经在跑时是 no-op——**解锁不会重新 `bind`** |

所以锁定期间客户端拿到的是一条 `[locked]` 响应（3.5 的设计，`IPCService.swift:15`、

`shutdown()` → `MCPIPCService.stop()` → `IPCServer.stop()`，那里对每条存活连接
`shutdown(SHUT_RDWR)`（`core/Sources/BrosisIPC/IPCServer.swift:140`）；崩溃 / 被杀由内核收尾。
app 重启是日常操作（改配置、升级、崩溃自动重开），**修复本身（客户端 `SO_NOSIGPIPE` + 重连）
对它仍然正确且必要，严重度仍按【阻塞】记**——所以这一轮只改文字，不改也不撤代码。

### 12.2 补的两个用例（都在 `MCPServiceTests`，纯进程内、不起 socket）

**① `testDroppedNeighborsDoNotConsumeTheNeighborQuota`**
（钉住 `Store.neighborRows` 的"多取候选"）

夹具里三个应用 10 s 一条轮着来，所以一条 Safari 观察**紧邻的前后两条都在白名单外**。
用例挑中间那条 Safari 观察（前后各还有 ≥ 3 条 Safari），要 `neighbors = 3`：

| 断言 | 为什么要它 |
|---|---|
| `apps = ["*"]` 时 `before` / `after` 各 3 条，其中**至多 1 条**是 Safari | 反向对照：坐实"白名单外的邻居密集"这个前提。没有这条，下面的断言可能是空断言 |

**② `testDayLedgerFlagsTheDayWhereTheGrantWindowStarts`**
（钉住 `StoreMCPService.runDayLedger` 的 `coversBeforeWindowStart`）

难点是"让窗口起点落在某天中间"必须**不依赖测试在几点跑**：`windowStart = now − 整数天`，
时区一变，它在当地的时刻就跟着变。用例的做法是**把 `store.retrieval.timeZone` 挪到
「此刻正好是当地正午」**（`TimeZone(secondsFromGMT:)`，按分钟取整），于是窗口起点
必定落在某天正午。然后在那天的窗口起点**前两小时放 6 条、后两小时放 6 条**：

| 断言 | 为什么要它 |
|---|---|
| 边界日 `coversBeforeWindowStart == true` | 正题 |
| 边界日 `observations == 12` | 标记不是摆设：**窗口起点之前的 6 条确实也在这个数里**（台账按自然日预聚合，切不成半天） |
| 同一天 `get_timeline(start = 窗口起点前 6 h, end = 当天末)` 只回 **6** 条，且 `appliedStart` 被抬到窗口起点 | 逐条查询的工具能裁、预聚合的台账不能裁——**12 与 6 的差就是这个标记要提醒调用方的事** |
| 整天都在窗口里的那天 `coversBeforeWindowStart == false` | 否则标记恒为真 = 等于没标 |

> **口径说明（与本轮任务书 C 条的字面表述不同，故写在这里）**：任务书 C 写的是
> "断言该日台账**不含**窗口起点之前的观察数与时长"，但同一份任务书的 E 条要求
