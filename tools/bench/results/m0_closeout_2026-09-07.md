## 4. 带入 M1 的清单

按来源分三组。

**A. 今天真实数据直接推出的**
1. Claude 桌面版 AX 为 0：先把 `com.anthropic.claudefordesktop` 加进 `AXSupport.chromiumFamilyBundleIDs` 重测；仍为 0 再走视口 OCR。
2. 飞书适配器：AX 树几乎为空（156 字符），按计划 3.3 做消息列表适配 + 视口 OCR；先确认 `AXManualAccessibility` 是否真的设成功。
3. 微信：AX 为空、超时多，直接按计划走视口 OCR + 气泡归属。
4. 访达 22% 超时：BFS 限深度 / 限节点后重测。
5. 定时兜底间隔 5 s → 10–15 s；`periodic` 与事件触发分别统计门控率，作为 E7 的常驻口径。
6. `completeness = complete` 的判定规则（现在没有一条 complete）。
7. 观察密度 8.4 条/分钟里 `app_deactivated` 占近三分之一且不带正文，M1 的 observations 表可以把它降为事件不建观察行。

**B. M0 计划内未做完的**
8. E5 正式对照：09-09 D2 清单出来后，对飞书、微信、Claude、Safari + 前几名做 A / B / C 对照，产出适配器名单与 OCR 阈值（D1 / D9 的最终校准）。
9. E1 真实题（D12）与 D8 判定；两阶段评估脚本。
10. E3 七个场景在 SQLCipher 加密库上复跑；真实取钥路径（钥匙串 + ACL）；锁定状态机。
11. E7 能耗成对测量（sudo）、真冷启动（sudo purge）。
12. E4 长期观察：月度再授权周期、路径型 TCC 可见性、Apple 事件实际发送。
13. iCloud 钥匙串可同步项在 Developer ID 签名下是否可用（D17 的"自动同步密钥"选项）。

**C. 环境与分发**
14. 家里机：装 Metal Toolchain（D26）、配 notarytool 凭据、下载或拷入 Qwen3.5-4B、探针跑满 3 天后重跑 `install.sh`。
15. Developer ID 证书 2027-02-01 到期前重签（公司机那张是 Xcode 按会员期签的）。
16. 下载器 / 校验器的 `autoreleasepool` 写法沿用到 M1 的模型管理器。

## 5. 出口结论

**Go，进入 M1**，附四条条件：
1. M1 第一周先做 E5 正式对照（等 09-09 的 D2 清单），适配器名单以它为准；在此之前 M1 只做不依赖适配器的部分（存储服务、SQLCipher、锁定状态机、检索、MCP 骨架）。
2. D8 与 D12 在 M1 期间用真实题关闭，向量相关工作在 D8 通过前不启动。
3. 能耗与冷启动两项由你在有 sudo 的场景补做，不阻塞 M1。
4. M1 工时按计划 5–7 周（90–140 h）不变，但 Air 上夜间任务的排期按 E9 Air 复测的降频吞吐（约 1,850 token/s）算，不按冷机数。

M1 的范围与验收见计划 4.2；建议下一步把 4.2 拆成可以逐个交给工作流的任务清单。
