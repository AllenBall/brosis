对应《实施计划》3.4 检索设计、实验 E2 的离线部分，落实《调研方案评审》F3。全部数据为本机实跑，脚本 `tools/bench/fts_compare.py`，查询集 `tools/bench/fts_queries.json`。

## 1. 环境与口径

| 项 | 值 |
|---|---|
| Python | 3.14.7 |
| SQLite 库版本（Python 链接） | 3.53.4 |
| 平台 | macOS-26.6.2-arm64-arm-64bit-Mach-O / arm64 |
| `trigram` + `detail=full` phrase 查询 | 可用 |
| `content='' , contentless_delete=1` | 可用 |
| jieba（方案 D） | 可用 |

口径说明：

- **真值**：相关 = 查询串按 ASCII 大小写不敏感的方式出现在 docs.text 中（Python: q.lower() in text.lower()）。真值在语料生成后由全表扫描重算，不是靠种植记录推断。
- **Recall@10** = 前 10 条命中的相关文档数 ÷ min(10, 相关文档总数)。相关文档超过 10 篇时按 10 封顶，所以这是「前 10 条能不能装满相关结果」，不是全量召回。
- **Recall_all** = 取前 5000 条时命中的相关文档数 ÷ 相关文档总数，衡量「索引本身能不能找到」，与排序无关。
- **Precision@10** = 前 10 条里相关文档占比，只对「应有结果」且**确实返回了结果**的查询统计；返回 0 条时 precision 无定义，漏检由 Recall@10 与「空结果正例数」两列体现。
- **空结果正例数** = 本该有结果却一条都没返回的查询数（分母是 58 条正例）。
- **报错率** = 该方案下抛 `sqlite3.OperationalError` 的查询数 ÷ 查询总数（F3 里的 phrase 错误就在这里体现）。
- **延迟**：`LIMIT 10` 的端到端 Python 侧墙钟时间，含建 SQL、绑参、取结果。冷 = 每次新建 `sqlite3.connect`（5 次/查询）；热 = 同一连接重复执行（20 次/查询）。**冷只清掉了 SQLite 自己的页缓存，没有清 macOS 的文件缓存**（清缓存需要提权），所以冷数字是下界。
- **索引体积** = 该方案的库文件字节数 − 只含 `docs` 表与精确字段索引的基准库字节数，两者都 `VACUUM` 后测量。
- **体积单位**：本文一律 2^20 进制，`MiB = 1024 KiB = 1,048,576 字节`，`GiB = 1024 MiB`；字节原值同时给出，换算不用猜。
- **子串匹配用 `LIKE '%q%' ESCAPE '\'` 而不是 `instr()`**：两者在本轮口径下等价（真值也是「正文包含该子串」，`%` `_` `\` 已转义），但 `LIKE` 在 SQLite 里对 ASCII 大小写不敏感，与精确字段列的 `COLLATE NOCASE` 口径一致；`instr()` 是大小写敏感的，会让英文查询的召回口径与 §7 的精确字段那一路对不上。产品实现用哪个都行，但要和真值口径保持同一个。

补扫描窗口「最近 7 天」覆盖 751 条 （23.5%）。补扫描是**并集**不是替代：扫描出来的精确子串命中排在前面，FTS 结果接在后面。走了补扫描的查询，其召回天然被窗口截断，§4/§5 里的 Recall 是对**全局**真值算的，所以这类查询在 X+E 下不会到 100%——这是设计如此，窗口内召回单列在 §6。各方案的阈值是按 §5 里纯 FTS 档的实测能力定的，不是统一拍的。

### 限定「时间窗口 + 应用」的扫描（`scan=app`）

计划 3.4 对一两字查询的回退是「限定**时间或应用**范围的扫描」。上表只限了时间窗口（最近 7 天 = 751 条），这一档再叠加应用限定，直接用 `docs(app, ts)` 复合索引先切范围再扫正文：

```sql
SELECT id FROM docs WHERE ts >= ? AND app = ? AND text LIKE ? ESCAPE '\'
ORDER BY ts DESC LIMIT ?;
```

## 7. 精确字段的查询计划

`EXPLAIN QUERY PLAN` 与热执行均值（基准库，3200 行，200 次取平均，`ANALYZE` 过）：

| 查询形态 | 计划 | 热均值 (ms) |
|---|---|---:|
| host 等值（裸域名查询） | `SEARCH docs USING COVERING INDEX idx_docs_host_ts (host=?)` | 0.007 |
| host 子域后缀 | `SCAN docs USING INDEX idx_docs_ts` | 0.257 |
| url 前缀（完整 URL 查询） | `SEARCH docs USING COVERING INDEX idx_docs_url_ts (url>? AND url<?) / USE TEMP B-TREE FOR ORDER BY` | 0.013 |
| url 子串 | `SCAN docs USING INDEX idx_docs_ts` | 0.088 |
| path 子串 | `SCAN docs USING INDEX idx_docs_ts` | 0.071 |
| 正文全表扫描 | `SCAN docs USING INDEX idx_docs_ts` | 2.929 |
| 正文限时扫描 | `SEARCH docs USING INDEX idx_docs_ts (ts>?)` | 0.550 |
| app 等值 + 时间窗口（走 idx_docs_app_ts） | `SEARCH docs USING COVERING INDEX idx_docs_app_ts (app=? AND ts>?)` | 0.010 |
| 正文限时 + 限应用扫描 | `SEARCH docs USING INDEX idx_docs_app_ts (app=? AND ts>?)` | 0.101 |

等值和前缀能走索引 seek，后缀/子串只能扫——但扫 `host`/`url`/`path` 这些窄列比扫 `text` 便宜得多，这就是把它们拆成独立列的价值（计划 3.4 第一条）。

**一个必须写进 schema 的细节**：`COLLATE NOCASE` 要写在**列**上，不能只写在索引上。SQLite 的 `col = ?` 用的是列的排序规则，列是 BINARY 而索引是 NOCASE 时，等值查询用不上那个索引。下面是 20,000 行的独立对照（内存库，`ANALYZE` 过，200 次热执行均值）：

| schema | `host = ?` 的计划 | 热均值 (ms) |
|---|---|---:|
| 索引 NOCASE、列 BINARY | `SCAN d USING COVERING INDEX i_host / USE TEMP B-TREE FOR ORDER BY` | 0.378 |
| 列与索引都 NOCASE | `SEARCH d USING COVERING INDEX i_host_ts (host=?)` | 0.003 |

差 **110 倍**（0.378 ms vs 0.003 ms，20,000 行）。行数越多差得越大，因为前者是全表扫。

## 9. 结论

### 9.1 F3 的三条结论在 3200 条语料上全部复现

- `trigram, detail=column`（原可行性报告选的配置）：68 条查询里 **54 条直接抛 `fts5: phrase queries are not supported (detail!=full)`**，报错率 79%，Recall@10 = 0。这个配置不能用。
- `unicode61` 原样：中文两字词 Recall@10 8.3%、中文三字以上 16.7%、单个汉字 0.0%。原因是 unicode61 把连续汉字当成一个 token（连中英之间也不断，`复核parseObservation的边界条件` 是一个 token），只有当目标词恰好被空格或标点隔成独立段时才命中。英文、标识符、URL、路径、错误码则 100%。
- `trigram, detail=full`：三字以上中文 100%，但**两字及一字查询恒为 0**（trigram 需要至少 3 个字符），而且不报错、静默返回 0 条——比报错更危险，必须在查询规划层显式拦截。

### 9.2 推荐方案

**推荐：B+E+V —— 汉字 bigram 预处理 + unicode61 + 精确字段列 + 单字补扫描 + 候选子串复核。**

| 指标 | B+E+V | 对比 |
|---|---|---|
| Recall@10 | 97.0% | C+E 91.5%，A+E 84.0%，D+E 99.7% |
| Precision@10 | 100.0% | 全表扫描 100%（真值定义即全表扫描） |
| 索引净增 | 0.99 MiB = 正文的 0.55 倍 | C（trigram）3.42 MiB = 1.88 倍，A 0.57 MiB，D 0.77 MiB |
| 建索引 | 预处理 315 ms + 写索引 32 ms（3200 条 / 1.82 MiB） | C 65 ms，D 预处理 1085 ms |
| 热查询 p50/p95 | 0.09 / 0.91 ms | 全表扫描 1.51 / 2.99 ms |
| 冷查询 p50/p95 | 0.23 / 1.20 ms | 冷含新建连接，见 §1 口径 |

理由：

1. **中文召回**：bigram 让 2 字及以上的中文查询恢复到 100%（A 只有 8.3% / 16.7%），而且不依赖词典，不会因为分词边界错位漏检。
2. **体积**：索引只有正文的 0.55 倍，trigram 是 1.88 倍——差 3.4 倍。在 5 GB 配额（3.8）下这是实打实的保留天数差异。
3. **不依赖第三方分词库**：bigram 是二十行代码，产品里用 Swift 重写没有风险；jieba 是 Python 库，不可能进 Swift app（Swift 原生替代见 §10）。
4. **复核是给 unicode61 忽略标点上保险**：`unicode61` 丢掉所有标点，`~/Library/Caches/brosis-build` 和 `~/Library/Caches/brosis-build` 在索引里是同一串 token。这条查询在 A+E 下前 10 条只有 2 条真的含该子串（Precision@10 20.0%），B+E 恰好排对了（100.0%）——但那是 bm25 文档长度归一化的运气，不是 bigram 的结构性优势，bigram 完全不改变非汉字部分的索引。加上复核后返回条数从 224 降到 172（= 相关文档总数 172），整套查询集的 Precision@10 由 100.0% 变为 100.0%（本轮两者都已满分，复核买的是「不靠运气」），代价是热 p95 从 0.90 ms 到 0.91 ms。默认打开。

**不推荐 trigram detail=full 作为主索引**，但它有一个真实优势：trigram 的 phrase 等价于精确子串，Precision 天然 100%，不需要复核。如果将来体积不再是约束，或者出现大量「任意子串」需求，它是唯一不需要额外复核的选项。现在的取舍是体积。

### 9.3 必须走精确字段或扫描的查询类别

| 查询类别 | 走哪条通道 | 依据 |
|---|---|---|
| URL、域名 | `urls` 表的 `canonical_url` / `host` 列，等值或前缀，走索引；再并上 FTS | 仅精确字段档 Recall_all 在 URL 类已有 96.9%，剩下的是「链接被人贴在聊天正文里」的情况，只能靠 FTS |
| 文件路径 | `files.path` 列 `LIKE`；再并上 FTS | 仅精确字段档在路径类 Recall_all 24.9%，大部分路径其实出现在终端回显和代码注释里，必须同时查正文 |
| 应用名、窗口标题 | `apps` / `windows` 规范化对象，等值 | 本轮未单独出题，但同理：这些是结构字段不是正文 |
| **单个汉字** | 必须走限定时间/应用范围的 `LIKE` 扫描 | bigram、trigram、unicode61 三种索引在单字类 Recall@10 都是 0（jieba 靠词典偶然拿到 80.0%，不可依赖）|
| 两字中文（若选 trigram） | 必须走扫描 | C 在两字类 Recall@10 0.0%，且静默返回空 |

扫描成本实测：全表 `LIKE` 在 3200 条 / 1.82 MiB 正文上热 p50 1.51 ms、p95 2.99 ms，吞吐约 **1204 MiB/s 正文**。按这个吞吐外推：正文 100 MiB 的库全表扫一次约 83 ms，1 GiB 约 0.9 s。所以单字查询必须限定范围——最近 7 天的窗口在本轮只占 23% 的行，实测 p95 0.62 ms；再叠加应用限定见 §6 的 `scan=app` 一档。**这些数字来自 1.82 MiB 语料，不能直接当作产品规模的结论**，M1 要在真实体量上复测。

### 9.4 给 T4 / T5 的建表语句

```sql
-- 原文：明文 TEXT，直接放在 SQLCipher 库里（计划 3.4：v1 不做 zstd BLOB 外部内容）
CREATE TABLE text_versions (
  id        INTEGER PRIMARY KEY,
  sha256    BLOB    NOT NULL UNIQUE,
  text      TEXT    NOT NULL,
  byte_len  INTEGER NOT NULL,
  created_at INTEGER NOT NULL
);

-- 全文索引：contentless（不重复存正文），bigram 预处理后的文本写进来。
-- contentless_delete=1 让删除可以只按 rowid 执行，配合 3.8 的级联删除。
-- 需要 SQLite >= 3.43；本机 3.53.4 已验证可用。
CREATE VIRTUAL TABLE text_fts USING fts5(
  body,
  tokenize = "unicode61 remove_diacritics 2",
  content = '',
  contentless_delete = 1
);
-- 写入：INSERT INTO text_fts(rowid, body) VALUES (:text_version_id, :bigrammed);
-- 删除：DELETE FROM text_fts WHERE rowid = :text_version_id;

-- 精确字段：独立列，不经 FTS（计划 3.4 第一条）。
-- COLLATE NOCASE 必须写在【列】上：`col = ?` 用的是列的排序规则，
-- 只给索引加 NOCASE 时等值查询走不了索引（§7 实测差 110 倍，两个数量级）。
CREATE TABLE urls (
  id            INTEGER PRIMARY KEY,
  raw_locator   TEXT NOT NULL,                 -- 原始定位信息，不做规范化
  canonical_url TEXT NOT NULL COLLATE NOCASE,
  host          TEXT COLLATE NOCASE,
  kind          TEXT
);
CREATE INDEX idx_urls_host  ON urls(host);           -- 裸域名等值：索引 seek
CREATE INDEX idx_urls_canon ON urls(canonical_url);  -- 完整 URL：前缀 LIKE 走范围

CREATE TABLE files (
  id   INTEGER PRIMARY KEY,
  path TEXT NOT NULL COLLATE NOCASE
);
CREATE INDEX idx_files_path ON files(path);  -- 子串 LIKE 仍是扫描，但只扫这一窄列

-- 扫描回退要用的复合索引（按时间/应用先切范围，再扫正文）
CREATE INDEX idx_obs_ts      ON observations(ts);
CREATE INDEX idx_obs_app_ts  ON observations(app_id, ts);
```

查询规划（`search(q, start, end, app, limit)`）按下面的顺序，全部结果取并集后去重：

```
1. q 形如 URL / 域名        -> urls.host 等值或后缀、urls.canonical_url 前缀/子串
2. q 形如路径               -> files.path 子串
3. q 是 1 个汉字            -> 在 [start,end] + app 范围内对 text_versions.text 做 LIKE 扫描
   （范围为空时拒绝执行，提示用户先缩小时间或应用范围）
4. 其余                     -> bigram(q) 包成 phrase 查 text_fts，按 bm25 取候选
5. 【只对第 4 步的 FTS 候选】用 LIKE '%q%' 复核精确子串，滤掉分词带来的假阳性
6. 1/2/3/5 四路结果取并集去重，按 bm25 / 时间倒序输出

第 5 步**不能**作用在第 1~3 步的结果上：那三路本身就是精确匹配，
urls/files 命中而正文里没抄这条 URL/路径是正常的，复核会把正确结果误删。
```

### 9.5 尚未验证、留给后续的点

- 本轮用的是 **Python 链接的 SQLite 3.53.4**，不是产品要用的 SQLCipher 构建。`contentless_delete`、trigram、bm25 都要在 E6 选定的 SQLCipher 上重新验证一次。
- 语料只有 3200 条 / 1.82 MiB，比真实库小两三个数量级。体积比例（索引/正文）在更大语料上会变，扫描延迟更会变。
- 真值口径是「精确子串」，对 OCR 错字、同义词、拼音输入没有任何覆盖。这些属于向量检索（D8）要解决的问题，不在本轮范围。
- 排序只用 bm25，没有做时间衰减、应用权重、去重合并。M1 的 `search` 要重新定排序。
- **`app` 列本轮只测了「限定扫描范围」这一种用法**（§6 的 `scan=app`）：没有出「列出某应用下全部内容」「按应用做 facet 过滤」这类题，也没有把 app 当成查询词（查「飞书」时命中的是正文里出现的这两个字，不是 `app = '飞书'`）。这两类查询要等 D12 的真实题到位后补。
- 子串匹配本轮用 `LIKE ... ESCAPE` 而不是规格里写的 `instr()`，理由见 §1 口径（语义等价，但 `LIKE` 对 ASCII 大小写不敏感，与精确字段列的 `COLLATE NOCASE` 一致）。产品换成 `instr()` 时要连真值口径一起换。
- 查询集是合成的（D12 真实题未提供）。真实题到位后必须复跑一次，别拿这版数字当最终结论。
