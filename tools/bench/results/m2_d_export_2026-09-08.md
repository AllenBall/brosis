## 1. 做了什么

### 1.1 一个新格式：`brosis-export` 归档**目录**（v1）

```text
<归档目录>/
├── manifest.json                 明文清单（格式版本、时刻、来源 device_id、范围、加密参数、
│                                 每块校验、总校验、清单 HMAC；**没有一个字节的正文**）
└── blocks/000000.blk             每块 ≤ 8 MiB 明文，AES-256-GCM
    blocks/000001.blk …
```

块文件字节布局：`magic "BRSEXP"`(6) + 块版本(1) + 保留 0(1) + AES-GCM combined（12 nonce + 密文 + 16 tag）。
明文是 JSON Lines，行首 `k` 是类型：`h` 块头、`t` 正文、`o` 观察（含 occurrence）、`d` 删除审计、
`s` 会话、`l` 台账、`p` 采集策略、`e` 运行期事件。

**目录 vs 单文件容器（3.8 要求二选一并写明）：选目录。** 四条理由：

1. 内存有上界——导出端一次只攒一块明文就落盘，导入端一次只解一块（实测见 §3）；
2. 坏一块能说清是哪一块（清单里每块一条 SHA-256，三种错误都带块号）；
3. 不输口令就能看清单——面对一堆归档不用一个个试口令；
4. 要"一个文件"时 Finder 右键压缩就是一个文件，反过来把容器拆成可校验的块得自己写解包器。

代价写在明处：归档是一个目录（拷贝时不能只拖一个文件）；清单明文暴露了**时间范围与 bundle id 名单**
（应用标识，不是内容）。

**与 D17 同步段文件（BRSSEG）借做法、不共用格式**：段文件是"两边 ack 就删的传输载体"，
归档是"三年后还要能打开的副本"，取舍不同，所以格式与版本号各走各的。共用一份实现会导致
以后改同步格式顺手改坏归档格式。

### 1.2 独立口令：第四把密钥，与前三把没有任何共同输入

| | 是什么 | 存在哪 |
|---|---|---|
| 库密钥 | 256 位随机 | data-protection 钥匙串 |
| 同步密钥 | 256 位随机 | 加密库里（`sync_state`） |
| 配对口令 | 24 字符 / 120 bit | 哪都不存 |
| **导出口令** | 用户自己想的 | **哪都不存**——不进钥匙串、不进库、不进清单、不进日志、不进事件、**不走命令行参数** |

```text
PBKDF2-HMAC-SHA256(口令, 16 字节随机盐, 600,000 次) → 32 字节 PRK
  ├─ HKDF-SHA256(PRK, "brosis-export/1 data")     → 数据密钥（封每一块）
  ├─ HKDF-SHA256(PRK, "brosis-export/1 manifest") → 清单的 HMAC-SHA256 密钥
  └─ HKDF-SHA256(PRK, "brosis-export/1 verify")   → 校验值，清单里只存它的 SHA-256
```

迭代数与"不用 Argon2id"的理由沿用 3.9（OWASP 2023 建议值；本轮不引第三方依赖，
系统里只有 CommonCrypto 的 PBKDF2）。**口令强度最低要求**：≥ 12 个字符、≥ 2 类字符
（小写 / 大写 / 数字 / 符号）、不能整条是同一个字符、≤ 1024 字符；
不合格**在派生密钥之前**就拒，一个字节都不写出去。导入端不查强度（老归档可能按更早的规则做的，
强度是导出时的门槛，不是解密的门槛）。

**代价说在明处**：口令丢了，归档永远打不开，没有找回通道。窗口文案里第一句就是这个。

### 1.3 四层校验，报错要能分辨

| 层 | 查什么 | 要口令 | 错误 |
|---|---|---|---|
| 0 | `verifier`（校验密钥的 SHA-256） | 是 | `wrongPassphrase` = **口令错**，一块都没读 |
| 1 | 每块密文 SHA-256 ↔ 清单 | 否 | `blockChecksumMismatch(seq:)` = 文件坏了 / 被改过 |
| 2 | 全部块校验和拼起来再哈希 ↔ `total_checksum` | 否 | `totalChecksumMismatch` = 少了一整块 / 换序 |
| 3 | 清单的 HMAC-SHA256 | 是 | `manifestTampered` = 口令对，但计数 / 范围 / 块列表被动过 |
| 4 | GCM tag（AAD = 归档身份 + 块位置 + 该块字节数与行数） | 是 | `blockDecryptFailed(seq:)` = 密钥不对或块被挪位 |

外加两条内容层：明文字节数与行数要对得上清单（`corruptBlock`）；每段正文的 SHA-256 要与它的 `sha`
对得上（把上面四层都重算过也拦得住）。

### 1.4 导出：分段读 + 起始水位线，**不是**快照事务

`Store` 是单连接 + 一把 `NSLock`。开长读事务的话 1 个月库要读上几秒到几十秒，
这段时间采集端一条都写不进来。所以导出**不开长事务**：开头取一次锁记下 `MAX(observations.id)`
当一致性边界（写进清单的 `scope.max_observation_id`），之后每批 200 条取一次锁，
加密与落盘都在锁外做，只导 `id ≤ 边界` 的行。

于是归档是库的一个**前缀**：导出开始之后写进来的观察不在里面——这是有意的，边界写在清单里可核对。

**导出**：`observations`（含用户删除的墓碑行）、`text_versions`、`occurrences`、`deletions`、
`sessions`、`ledgers`，可选 `app_policies` 与运行期事件。

**不导出**：`capture_audit` / `capture_stats`（本机采集质量度量，不是证据）、
`mcp_audit`（授权与访问审计，里面有客户端 id 与对端签名信息；归档是要拿出机器的东西，
把访问审计一起带走只扩大敏感面、不增加证据价值）、`grants`（各机独立配置）、
`sync_state` / `sync_peers`（同上，而且 `sync_state` 里存着**同步密钥**——它绝不能进一份
用另一把口令保护的归档）、`chunks` / `vec_chunks`（本机派生数据，删了能重建）、缩略图文件。

**范围**：时间半开区间作用在 `observations.ts`；应用用 bundle id 白名单。
会话按 `start` 落在窗口内过滤，台账按 `period` 与窗口两端换算出的日 / ISO 周标签比较。
**限定应用范围时不导 `deletions` / `sessions` / `ledgers`**——删除审计的目标是观察 id、
会话与台账是整条时间线，都无法按应用切开（切开就会在导入端删掉或算错范围外的记录）。
这一条会写进清单的 `notes`。

**脱敏照常生效但不额外做**：正文入库前已经过 app 的 `Redactor`，库里存的就是脱敏后的那一份，
归档原样搬——不二次脱敏、也不还原。

### 1.5 导入：恢复与合并两种模式

| | 恢复 `restore` | 合并 `merge` |
|---|---|---|
| 触发 | 目标库没有观察 / 正文 / occurrence / 删除审计 / 会话 / 台账 | 其他一切情况 |
| observation id | **原样写回**源 id，origin 两列照抄 | T13 口径：本机新 id + `(origin_device, origin_id)`；归档来自本机自己时按源 id 写回、origin 留 NULL |
| 幂等 | 归档粒度（`export_imports.archive_id`） | 归档粒度 + 逐条身份判定 |
| sessions / ledgers | 原样导入 | **不导**（派生结果各机自算，3.9 同一条口径） |
| 运行期事件 | 原样导入 | 不导（`jobs` 没有跨库主键） |
| `app_policies` | 覆盖式 | 只补缺失的，不覆盖本机策略 |
| 用户删除墓碑 | 原样写审计行（归档里的观察本来就带 `deleted_at`） | 写审计行**并在本机副本上重放级联**，审计行计数按本机实得重写 |

**不复活已删除的记录**：目标库里已经有这条记录（哪怕只剩墓碑）就跳过。3.8 的删除是合规动作，
导一份更早的归档不该悄悄撤销它。

**事务粒度**：一块一个事务，块内失败整块回滚。正文在归档内**全局去重**（不像段文件每段自包含），
且总排在第一次引用它的观察之前，所以后面的块解析时那条正文要么已在库里、要么就在本块里。
收尾把"插进来却没有任何 occurrence 的正文"扫掉。

**schema 版本**：v1 的归档只在同一个 schema 版本之间导入导出；清单里的 `schema_version`
或归档格式 `version` 与本版本不同就直接拒绝，不猜着读、不自动迁移。

### 1.6 schema v8：`export_imports`

一张新表（纯新增，老库就地补建）记"这个库导入过哪些归档"。
**为什么恢复模式需要它**：合并模式的逐条判据是 `(origin_device, origin_id)`，
恢复写回的记录 `origin_device` 是 NULL、看起来就是"本机自己产生的"，逐条判定认不出重复，
再导一次就会翻倍。所以再加一层归档粒度的幂等。顺带也是审计。

> v7 是 d 批留给 T15 的号，T15 没用到就空着。`Schema.migrationVersions = [1,2,3,4,5,6,8]`
> 是唯一一份清单，三处断言"migrations 表每版一行"的用例都改成按它数（原来写死 `1...version`）。

### 1.7 D7 配额联动（数据层，UI 由主会话接）

```swift
let action = try store.quotaAction()          // 等级 / 用量 / 会删掉哪一段 / 建议导出范围 / 一行文案
try store.acknowledgeQuotaAction(archiveID:)  // 用户确认（可附上"我已经先导出了"的归档 id）
switch try store.expireAfterNotice() {        // 没确认过就 .blocked，**不删**
case .notNeeded, .blocked, .expired: …
}
```

- 等级：`< 80%` ok、`≥ 80%` warning、`> 100%` full（按原文净载荷，与 2.4 / `expire()` 同口径）。
- `wouldDeleteObservations` 是**估算**（按平均每条观察多少字节倒推），不逐条模拟；
  真正删多少由 `expire()` 当场决定，这个数字只用来写通知与建议导出范围。
- 事件只在**跨档**时写一条（`quota_warning` / `quota_full`），同一档反复查不刷爆 `jobs`。
- `expire()` 本身语义**没有变**（夜间任务与压测还用它），`expireAfterNotice()` 是产品路径多的那一层。
- 确认**只管一次**：删完就清掉。
- `QuotaAction.message` 在 full 那一档必然包含「先做一次加密导出」与「不会影响已经导出的副本」。

```bash

def norm(x):
    if isinstance(x,dict): return {k:norm(v) for k,v in x.items() if 'elapsed' not in k}
    if isinstance(x,list): return [norm(v) for v in x]
    return x
print("search-batch 逐项相同", norm(json.load(open(R+"/search_A.json")))==norm(json.load(open(R+"/search_D.json"))))
a=json.load(open(R+"/stats_A.json")); d=json.load(open(R+"/stats_D.json"))
keys=['observations','live_observations','tombstoned_observations','text_versions','occurrences','fts_rows','deletions','text_payload_bytes']

print("check", json.load(open(R+"/check_D.json"))['all_passed'])
```

  占大头的是每条观察的字段）——与 D17 段文件的 154.4% 同一量级，低一点是因为
  归档内正文**全局去重**、没有段文件那 +5.05% 的自包含重复；
- **AEAD 的净开销 = 1,064 B**（38 × (12 nonce + 16 tag)），加上 38 × 8 B 块头与 9,080 B 清单，
  密文相对明文只涨 **0.0033%**。
- 每条观察平均 **1,222 B** 归档字节。

峰值内存的两个杠杆（都是实测）：

| 配置 | 峰值 footprint |
|---|---|
| 默认（`--cache-kib 131072` = 128 MiB 页缓存），全库 | 538,920,016 B = 514.0 MiB |
| `--cache-kib 8192`（8 MiB 页缓存），全库 | 371,868,632 B = **354.6 MiB** |
| 默认页缓存，只导 7 天（60,480 条 / 9 块 / 73,469,380 B） | 251,331,352 B = **239.7 MiB**，1.83 s |

也就是说峰值 ≈ 页缓存 + 随导出条数缓慢增长的那一部分（归档内去重表 + 分配器保留）。
要压到 250 MiB 以下有两条现成的路：调小页缓存，或按时间分批导。**不随块大小增长**——
一次只攒一块明文（8 MiB）就落盘，这是选"目录"而不是单文件容器换来的。

### 3.4 校验与导入

| 项 | 数字 |
|---|---|
| `export-verify`（逐块解密 + 字节数 / 行数 / 计数对账，不写库）〔注〕 | **4.32 s**（进程 real 5.04 s），峰值 footprint 58,278,440 B = **55.6 MiB** |
| `export-info`（只读清单，**不需要口令**） | 进程 real **0.00–0.01 s** |
| 一次 PBKDF2 600,000 + HKDF | 进程 real **0.09 s**（三次一致；`export-info` 是 0.00 s，差值就是 KDF） |
| **导入到空库**（恢复模式） | **34.65 s**（进程 real 34.68 s，7,481 条/s），峰值 footprint 242,893,568 B = **231.6 MiB** |
| 再导一次同一份归档 | `already_imported = true`，**87.5 ms**（进程 real 0.09 s，其中 85 ms 是 KDF），一行不动 |
| 恢复出来的库文件 | 520,552,448 B = 496.4 MiB（源库 516.8 MiB，**小 3.9%**——源库经历过一次删除，页里有洞） |

〔注〕`export-verify` 那一行量的是**同一个库的第一份导出**（同样 38 块、体积差 33 KB，
差别只是量之前又重算了一遍台账）；导出侧的两处提速是在它之后做的，只影响导出、不影响校验。

导入比 `import-jsonl` 建库慢 —— 34.65 s vs 51.81 s，其实**快 33%**：归档里正文已经去重过
（81,422 条正文 + 113,280 次按 sha 复用），而 JSONL 要为 221,716 条正文各算一次 SHA-256。
峰值内存只有建库的 28%（231.6 vs 816.4 MiB），因为一次只解一块。

```text

[PASS] 弱口令被拒，且一个字节都没写出去：门槛：≥ 12 字符 / ≥ 2 类字符
[PASS] 导出成功（1 条观察 / 1 块）：archive_bytes=2301
[PASS] manifest 不需要口令就能读，且不含密钥材料：AES-256-GCM / PBKDF2-HMAC-SHA256 ×600000
[PASS] 归档目录里搜不到正文、脱敏前明文与口令（含阳性对照）：命中 0 次；阳性对照 archive_id 命中 1 次
[PASS] 口令错误 → 明确报口令错，不泄漏内容
[PASS] 往返一致：恢复模式、id 原样、正文逐字节相同：mode=restore inserted=1
[PASS] 导入后一致性检查全过
[PASS] 同一份归档再导一次不翻倍：already_imported=true observations=1
[PASS] 源库删掉之后：库里查不到，归档仍然完整（删除不影响已导出的副本）
[PASS] 篡改一字节 → 校验失败并拒绝：block seq=0
[PASS] 配额满：通知带「先加密导出」，且没确认前不删（D7 / 3.8）：used=1806 quota=512 would_delete=3
[PASS] 确认之后才真的按最旧先删：确认只管一次，删完就失效
```

（口令、脱敏前的密钥、检索锚点三串都是**运行时拼接**的，不以字面量形式留在二进制里。）

## 4. 压测过程中发现并修掉的一个真问题

**症状**：1 个月库往返之后，30 天日台账里有 **24 天的 `sessions` 比源库少 1**，
而两边的 `sessions` 表逐行相同（8,285 行、1,057 行 stale、内容与 id 全等）。

**原因**：`Store+Sessions.sessionRows` 的区间查询要给 `start` 补下界（E7 §10.3：
不补下界时 12 个月库 6.42 ms，补了 0.07 ms），下界用的是 `meta.sessions_max_duration_ms`。
这个键是 `buildSessions()` 写的**派生水位线**，不在 `sessions` 表里。恢复出来的库只有表、没有键，
下界退化成 0，于是"起点在窗口之前、终点落在窗口里"的那条会话查不到。

**修法**：恢复模式导完会话之后，按导进来的行**重算**两个键
（`sessions_max_duration_ms = MAX("end" - start)`、
`sessions_watermark_ts = MAX(ts)` 的活着的本机观察），再顺手写一条 `sessions_config`。
两个键都**不进归档**——它们从行本身算得出来，存进去只会多一处要长期兼容的字段，还可能与行不一致。

**回归**：`ExportTests.testRoundTripIntoEmptyDatabase` 里加了两组断言
（两个 meta 键存在且与源库相等；四个"窗口起点落在会话中间"的区间查询两边 id 列表相等），
变异检验见 §6。修完之后 1 个月库上 **30/30 天台账逐项相同**。

顺带做的两处提速（都在导出侧，行为不变）：
occurrence 取数语句改成**一批准备一次 + reset 重绑**（原来每条观察 `sqlite3_prepare` 一次，
1 个月库就是 25.9 万次），全库导出 8.85 s → **7.35 s**；
块缓冲区一次 `reserveCapacity` + `removeAll(keepingCapacity:)` 复用（少了每块约 20 次翻倍重分配）。

## 5. 未做与原因

1. **app 窗口里没有"导入归档"入口**。导入是恢复动作，产品路径要先想清楚"往哪个库恢复、
   恢复到一半怎么办、要不要新建数据目录"；数据层已经做好（`Store.importArchive`），
   命令行入口是 `brosis-store import`（目标库不存在时按清单的 `source_device` 建库）。
2. **归档不做压缩**。与 D17 段文件同一个理由：本轮不引第三方依赖（系统里没有 zstd），
   Apple 的 `Compression` 框架能用，但会在格式上多加一层要长期兼容的东西。
   实测归档 / 原文净载荷 = 149.3%，压缩的收益值不值得下一轮再说。
3. **归档格式只做同 schema 版本的导入导出**。跨版本迁移（v8 的归档导进将来的 v9 库）
   是一件独立的事：要么在导入端写迁移，要么在导出端写降级，两条都要有自己的测试矩阵。
   现在的行为是**明确拒绝**（`schemaMismatch`），不猜着读。
4. **恢复模式要求目标库是空的**。往一个已经有数据的库里"按源 id 恢复"会撞主键；
   有数据时自动走合并模式（id 换成本机空间 + origin 两列）。
   代价：合并进来的记录本机 id 与源库不同，跨库对同一条记录说话要用 origin 两列。
5. **恢复出来的库再合并同源的另一份归档会重复**——如果那个库的 `device_id` 与源库不同。
   `brosis-store import` 在新建库时会自动用清单里的 `source_device`，走这条路就没有这个问题；
   手工指定别的 `--device-id` 时会。已知边界，写在这里。
6. **`wouldDeleteObservations` 是估算**（见 §1.7），不是逐条模拟的精确值。
7. **没有跑 12 个月库**。1 个月的数字线性外推是 3.6 GiB 归档 / 88 s 导出 / 7 分钟导入；
   12 个月的实测归 T17（那一条本来就在 T17 的范围里）。
8. **窗口没有自定义起止时刻**，只有三档预设（全部 / 最近 30 天 / 最近 90 天）；
   `ExportRequest` 本身支持任意区间，命令行 `--start` / `--end` 已经能用。
9. **没有真机点过窗口**（本轮约束：屏幕锁定、不启动 GUI）。窗口代码编译通过、
   逻辑那一半（口令强度、文案、范围换算）由自检与单测覆盖，**真机点一遍留给主会话**。

## 6. 变异检验（验收者可复制到自己的 scratch 再改）

三条，都是"把代码改坏之后测试必须红"。**改动一律在 scratch 的副本上做，不动项目目录**：

## 8. 对计划的影响

**一句话**：3.8 的「加密导出 + 删除不覆盖已导出副本」与 D7 的「删前通知并可先加密导出」
在数据层与命令行上全部落地并有实测数字（1 个月库导出 7.35 s / 302 MiB、导入 34.65 s、
往返 55 题检索与 30 天台账逐项相同），M3 的「加密导出」可以提前销账；
仍挂在 M3 的只剩两件小事——app 窗口里的导入入口，以及真机点一遍窗口。
