# T7-Air · E9 在 M4 Air（16 GiB / 无风扇）上的复测 + 真实 Metal Toolchain 的 metallib 体积

- 日期：2026-09-07
- 对应：`tools/e9/README.md` 末尾「Air（M4 / 16 GB，无风扇）复测清单」第 1–8 项；`docs/实施计划.md` 的 **D26**（Metal Toolchain 与 metallib）、**D27**（推理运行时内存策略）、**D17**（跨设备共享向量）、3.11（模型管理器与 app 体积）

### 一句话结论

**E9 在 Air 上全部机制成立，内存与体积两项比预期好很多（D26 装 Metal Toolchain 的收益是 app 从 159.55 MiB 降到 43.12 MiB；D27 的 256 MiB 缓存上限在 16 GiB 上峰值只有 1.61 GiB、不进 swap），唯一必须改计划的是吞吐与热降频：Air 冷机只有 Max 的 23.9%，持续 2 分钟后再掉三分之一。**

### 3.4 内存与吞吐（清单第 2、3 项）

**跑的顺序就是任务要求的顺序**：`--cache-limit-mib 256` → `--cache-limit-mib 0` → 默认（不给该选项）。每档前后都记了 `memory_pressure | tail -5` 与 `sysctl vm.swapusage`（文件 `sysmem_bench_*_before/after.txt`）。

| 缓冲池上限 | **峰值 footprint（决策用）** | 峰值 RSS（参考，低估） | MLX GPU 峰值 / 结束时缓冲池 | 吞吐 | Max 基线的 footprint / 吞吐 |
|---|---|---|---|---|---|
| **256 MiB** | **1,730,626,760 字节 = 1,650.5 MiB = 1.612 GiB** | 800,980,992 字节 = 763.9 MiB | 1,245.1 MiB / 253.7 MiB | **16.32 条/s、2,866 token/s** | 1,992.4 MiB = 1.95 GiB / 68.25 条/s |
| **0（关掉）** | **1,467,204,808 字节 = 1,399.2 MiB = 1.366 GiB** | 800,882,688 字节 = 763.8 MiB | 1,245.1 MiB / 0 MiB | 15.90 条/s、2,791 token/s | 1,839.0 MiB = 1.80 GiB / 65.73 条/s |
| **默认（不限）** | **5,918,655,760 字节 = 5,644.5 MiB = 5.512 GiB** | 800,899,072 字节 = 763.8 MiB | 1,245.1 MiB / **4,893.8 MiB** | 16.23 条/s、2,849 token/s | 6,355.9 MiB = 6.21 GiB / 70.22 条/s |

要点：

- **三档全程没有 swap**：`vm.swapusage` 前后都是 `total = 0.00M used = 0.00M`；`memory_pressure` 空闲率 82% → 80%，从未进 warn / critical。**默认档 5.51 GiB 在 16 GiB 机器上也扛得住**（跑之前空闲 82%），但没有理由这么用。
- **程序内 `ledger_phys_footprint_peak` 与 `/usr/bin/time -l` 的 `peak memory footprint` 完全一致**（例如 256 档两边都是 5,918,655,760 / 1,730,626,760 字节），两条路互为交叉验证。
- **RSS 低估 3.4–7.4 倍**：默认档 footprint 5,644.5 MiB 而 RSS 只有 763.8 MiB。F8 的口径结论在 Air 上同样成立。
- **`Memory.clearCache()` 有效**：256 档跑完 footprint 从 1,000.3 MiB 掉到 **745.5 MiB**，缓冲池 253.7 → 0 MiB；默认档从 5,644.5 掉到 **750.6 MiB**。D27 的「跑完立刻还内存」在 Air 上照样成立。
- **Air 上三档之间的吞吐差别落在噪声里**（16.32 / 15.90 / 16.23 条/s，极差 2.6%），因为同一批测量里温漂已经有这个量级。Max 上「限缓存掉 2.8%、关缓存掉 6.4%」的结论在 Air 上**测不出显著性**，但方向一致（关缓存最慢）。**结论不变：256 MiB 是免费的**。
- **单条嵌入**峰值 footprint **751.7 MiB**（10 次里的最大值），RSS 762.5 MiB。比 Max 的 888.4 MiB **低 136.7 MiB**，其中约 116.7 MiB 可以用 metallib 体积差解释（全量 metallib 会被映射进进程）。
- `gpuPeakMiB` 在 Air 是 1,245.1 MiB，Max 是 1,443.3 MiB，同一份语料、同一批构造下不同——MLX 的分配策略与设备有关，**但不影响数值**（第 2 节第 8 项已证明向量逐位相同）。

**按吞吐重算工期**：Max 上 12,328 token/s → 100 万 token 约 81 s。Air 冷机 2,866 token/s → **349 s（5.8 分钟）**；持续负载降频后按后 5 轮均值 1,852 token/s → **540 s（9.0 分钟）**，最差那轮 1,365 token/s → **12.2 分钟**。也就是说 **Air 上「日均 100 万 token 正文嵌入」正好卡在计划「日均 GPU < 10 分钟」的线上**，M1 排期必须按降频后的数算，不能按冷机数算。

### 3.5 热状态（清单第 4 项）—— Air 独有的结论

**方法**：连续 606 s（约 10 分钟）循环跑 `bench --id ... --cache-limit-mib 256`，共 **46 轮**；每轮记录进程侧的 `ProcessInfo.thermalState`（`environment.thermalStateAtStart` 与 `memoryAtEnd.thermalState`）与当轮吞吐，并在每轮后采样 `pmset -g therm` 与 `memory_pressure`。**`powermetrics` 需要 sudo，未用**；`sysctl` 下本机没有 `machdep.xcpm.cpu_thermal_level` 之类的节点（`sysctl -a | grep -i thermal` 无输出），所以系统侧只有 `pmset -g therm` 一条路。

| 时间点（负载开始后） | 轮次 | `thermalState` | 吞吐 |
|---|---|---|---|
| 0 – 119 s | 1 – 11 | `nominal` | 16.32 → 15.10 条/s |
| **130 s（2 分 10 秒，wall 02:21:20Z）** | **12** | **进程结束时首次变 `fair`** | 14.21 条/s |
| 141 – 606 s | 13 – 46 | **全程 `fair`**（起、终都是） | 15.26 → 8.47 条/s，抖动大 |
| 全程 | — | **从未出现 `serious` / `critical`** | 最低 **7.78 条/s**（第 41 轮，509 s 处） |
| 负载结束后静置 5 分钟 | 恢复轮 | **回到 `nominal`** | **15.58 条/s**（冷机的 95.5%） |

- 前 5 轮均值 **15.90 条/s / 2,792 token/s**，后 5 轮均值 **10.55 条/s / 1,852 token/s**，**衰减 33.6%**；最差轮相对冷机 **−52%**。
- **`pmset -g therm` 全程都是 `No thermal warning level has been recorded`**，即系统没有记录到「热警告等级」。所以**在 Air 上判断降频要用 `ProcessInfo.thermalState` + 实测吞吐，不能指望 `pmset`**。
- 每轮的 `peakFootprintMiB` 在 1,621.1 – 1,662.0 MiB 之间稳定（256 MiB 档），**降频不改内存**；全程 `vm.swapusage` 仍是 0。
- 系统内存空闲率从 81% 缓慢降到 64%（文件缓存增长），**没有进 warn/critical**。
- **告警**：本机在测试期间是用户的工作机，后台可能有其他负载（`uptime` 载荷在测前是 1.49 / 6.03 / 7.54）。吞吐衰减里可能混入了一点外部干扰，但 `thermalState` 由系统给出，且「静置 5 分钟即恢复」这条强烈支持「是热，不是别的」。

| 下载（直连，15 个文件） | 649,088,604 字节 = 619.02 MiB / **50.20 s = 12.33 MiB/s** | 54.66 s = 11.33 MiB/s |
| ├ 其中 `model.safetensors` | 633,152,041 字节 = 603.82 MiB / 38.45 s = **15.71 MiB/s** | 41.63 s = 14.51 MiB/s |
| └ sha256 | **15/15 与清单一致** | 同 |
| 镜像 + 断点续传（`--force-base https://hf-mirror.com --simulate-interrupt 41943040`） | 619.02 MiB / **58.68 s = 10.55 MiB/s**；`model.safetensors` 42.06 s = 14.36 MiB/s | 镜像 52.80 s = 11.72 MiB/s |
| └ **续传证据** | `resumedFromBytes = 41,943,040`（40.00 MiB），**`rangeStatus = HTTP 206`**，整文件 sha256 与清单一致 | 同 |
| `verify`（已装模型全量重校验） | **0.264 s**，15/15 `allMatch: true` | 0.247 s |

说明：

- 工具的 `download` 子命令**没有「只下一部分文件」的选项**，`--simulate-interrupt` 只作用于 `model.safetensors`（先写前 N 字节再走 Range 续传），整个仓库仍然会完整下一遍。所以「镜像 + 续传」这一次是**完整的第二遍下载**，为了不覆盖直连那份，用 `BROSIS_E9_MODELS=~/Library/Caches/brosis-build/e9/models-mirror` 装到了另一个根。
- **这份镜像副本还在**（631.24 MiB，`~/Library/Caches/brosis-build/e9/models-mirror/`），审核者复跑完可以直接删，它只是验证产物。
- 两遍都经系统代理 `127.0.0.1:<port>`，所以速率反映的是**这条代理链路**，不是裸网络。

### 4.4 内存与吞吐（三档，顺序 256 → 0 → 默认）

```bash
for L in "--cache-limit-mib 256" "--cache-limit-mib 0" ""; do
  memory_pressure | tail -5 ; sysctl vm.swapusage ; vm_stat        # 之前
  /usr/bin/time -l "$APP" bench --id Qwen3-Embedding-0.6B-8bit $L \
    --out $R/air_bench_<档>.json --crosscheck-out $R/air_vec_<档>.json \
    > $R/air_bench_<档>_stdout.json 2> $R/air_bench_<档>_stderr.txt
  memory_pressure | tail -5 ; sysctl vm.swapusage ; vm_stat        # 之后
done
```

原始文件：`air_bench_cache256.json` / `air_bench_cache0.json` / `air_bench_default.json`，各自的 `_stderr.txt`（`/usr/bin/time -l` 全文，含 `maximum resident set size` 与 `peak memory footprint` 两行），对照向量 `air_vec_cache256.json` / `air_vec_cache0.json` / `air_vec_default.json`（各 20 条 × 1024 维），系统内存 `sysmem_bench_{cache256,cache0,default}_{before,after}.txt`。

**批 8 / 批 4 没做，原因是工具不支持，不是漏做。** `main.swift` 里 `bench` 只解析 `--id` / `--dir` / `--out` / `--crosscheck-out` / `--cache-limit-mib`，没有批大小选项。`Bench.swift` 里批大小是**写死**的：

| 用途 | 写死的批大小 | 出处 |
|---|---|---|
| 吞吐 `throughput` | **`texts.count` = 16**（`corpus.throughput` 的全部 16 条一次成批） | `Bench.throughput`：`e.embedBatch(texts)` |
| 确定性 `determinism` | **8** 与 **1**（就是靠这两档比出 4.04×10⁻⁴ 的差） | `Bench.determinism`：`embedAll(..., batchSize: 8)` / `batchSize: 1` |
| 语义 `semantics` | **10** | `Bench.semantics`：`embedAll(..., batchSize: 10)` |
| MRL | **16** | `Bench.mrl`：`embedAll(..., batchSize: 16)` |
| 对照向量导出 | **8** | `Bench.crosscheckDump` |

要找 GPU 峰值随批大小的拐点，得先给 `bench` 加一个 `--batch-size` 选项（改 `Bench.throughput` 的签名，把 `texts` 切片）。**建议放进 M1 的第一批小改动**，因为 Air 上「批多大最省内存又不掉吞吐」直接决定 D27 的建议值。

## 6. 对计划的影响（各一句话）

- **D26（Metal Toolchain 与 metallib）**：**建议直接批准并写进发版流程**——装了之后 `build_app.sh` 自动走 `xcrun metal` 现编，metallib 从借来的 119.64 MiB 降到 **2.99 MiB**、app 从 159.55 MiB 降到 **43.12 MiB**（−73%），而且版本与运行时严格对齐（不再是 0.31.2 对 0.31.1 的错配），构建只多 5 秒；159.6 MiB 这个「上限」可以从计划里划掉了。
- **D27（推理运行时内存策略）**：**维持原案，实机确认可行**——Air 16 GiB 上 `--cache-limit-mib 256` 峰值只有 **1.61 GiB**（比 Max 的 1.95 GiB 还低）、吞吐无显著损失、全程零 swap、`clearCache()` 后回落到 745.5 MiB；同时补一条 Air 专属的**热门控**：持续负载 2 分 10 秒后 `thermalState` 变 `fair`、吞吐掉 33.6%（最差 52%），所以 M1 的夜间任务要按降频后的 ~1,850 token/s 排期（100 万 token ≈ 9 分钟，正好卡在「日均 GPU < 10 分钟」的线上），并在 `thermalState != nominal` 时降批或暂停。
- **3.11（模型管理器与 app 体积）**：**体积目标提前达成**——app 43.12 MiB + 模型 619.02 MiB = 0.6466 GiB，加 D7 的 10 GiB 原文配额后本机仍余 56.03 GiB；下载器在公司网络下直连 12.33 MiB/s、镜像 10.55 MiB/s、Range 续传 HTTP 206、15 个文件 sha256 全对，三项机制无需改动。
- **D17（跨设备共享向量）**：**意外利好**——M4 Air 与 M4 Max 在同一 MLX 版本、同一批构造下**逐位相同**（前 8 维、40 对余弦、MRL、determinism 的最大绝对差全部为 0 或完全一致），所以跨设备共享向量不必先按「只能比余弦」设计；但**批构造必须固定**这条不变（换批大小仍差 4.04×10⁻⁴），整向量文件的逐位对照待家里机拷 crosscheck 向量后补齐。
