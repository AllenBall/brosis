## 1. 【发布阻断】`Bundle.module` 在离开构建机后必崩

### 1.1 病因

SwiftPM 给带 `resources:` 的目标生成的访问器（原文在
`<任一 scratch>/arm64-apple-macosx/release/BrosisModels.build/DerivedSources/resource_bundle_accessor.swift`）
只查两个地方：

```swift
let mainPath  = Bundle.main.bundleURL.appendingPathComponent("brosis_BrosisModels.bundle").path
let buildPath = "<编译时的绝对构建目录>/release/brosis_BrosisModels.bundle"
guard let bundle = Bundle(path: mainPath) ?? Bundle(path: buildPath) else { Swift.fatalError(...) }
```

对 `.app` 来说 `Bundle.main.bundleURL` 是 `brosis.app/` **这一层**，而 `build_app.sh` 把资源
bundle 拷进的是 `Contents/Resources/`——不在候选里。于是打包好的 `.app` 只是**借着编译期写死的
构建目录**才没崩：构建目录一旦改名 / 删掉 / 换台机器（用户装 DMG），任何一次 `Bundle.module`
求值都直接 `fatalError`，进程 exit 133。

`app/Sources/BrosisModels/ModelsUtil.swift` 原来那串"多路候选"救不了：第一步
`candidates.append(Bundle.module.bundleURL…)` 就已经求值了 `Bundle.module`。

**`.app` 根目录能不能放东西？不能——本次实跑证伪**（这是原结果文件里列的修法 ①）：

```text
$ cp -R brosis.app/Contents/Resources/brosis_BrosisModels.bundle brosis.app/
$ codesign --verify --deep --strict brosis.app
brosis.app: unsealed contents present in the bundle root
$ codesign --force --sign "<Developer ID>" --options runtime brosis.app
brosis.app: unsealed contents present in the bundle root        # 连重新签都签不动
```

换成**符号链接**同样被拒（同一句 `unsealed contents present in the bundle root`）。
所以只剩"自己找 + 加闸门"这条路（原结果文件的修法 ② + ③）。

### 1.2 改法一：`ModelResources` 自己按目录顺序找，`Bundle.module` 只在确认不会崩时才碰

`app/Sources/BrosisModels/ModelsUtil.swift` 的 `ModelResources` 重写为：

| 顺序 | 候选目录 | 谁走这一条 |
|---:|---|---|
| 1 | `BROSIS_MODEL_RESOURCES`（环境变量，指向目录） | 测试与验收 |
| 2 | `Bundle.main.resourceURL` | **产品路径**：`.app/Contents/Resources` |
| 3 | `Bundle.main.bundleURL` | 裸可执行文件（构建目录里直接跑） |
| 4 | 可执行文件所在目录的 `../Resources` | `Contents/MacOS/` 里的 `brosis-embed` 兜底 |
| 5 | 可执行文件所在目录本身 | 同上 |
| 6 | `Bundle.main.bundleURL` 的上一级 | `swift test`：`.xctest` 与资源 bundle 是构建目录里的兄弟 |
| 7 | `Bundle.module`（**最后**） | 只在 SwiftPM 布局换成结构化 bundle 时才需要 |

每个根目录先看 `brosis_BrosisModels.bundle/<name>`，再看平铺的 `<name>`
（`build_app.sh` 会把 `catalog.json` 另外平铺放一份到 `Contents/Resources/`）。

第 7 条的安全阀是 `safeModuleBundle`：**先自己确认访问器的第一候选
（`Bundle.main.bundleURL/brosis_BrosisModels.bundle`）存在，才敢碰 `Bundle.module`**；
不存在就返回 `nil`。访问器的第二候选是编译期写死的构建目录，运行期看不见、也不该去赌
——正是它让"离开构建机就崩"这件事一直没被发现。

全部候选都没有时返回 `nil`，`Catalog.load()` 抛 `ModelsError`（消息里把真正试过的目录逐条列出），
**不再 fatalError**；调用方按 3.11 的降级表把模型相关功能显示为「未启用」。

### 1.3 改法二：`build_app.sh` 第 4d 步——**把构建目录临时改名再跑一遍**

签名与验证做完之后：

```text
==> 4d. 把构建目录临时改名，再跑一遍（证明 .app 不依赖构建目录）
  构建目录已改名：arm64-apple-macosx -> arm64-apple-macosx.build-gate-hidden
  --self-check：通过（172 项，全部 PASS）
PASS bundle 内 GPU 冒烟 300（metallib Resources/mlx-swift_Cmlx.bundle/default.metallib）、
     sqlite-vec v0.1.9、清单 3 项、向量 512 维 int8
  brosis-embed selftest：passed
  构建目录已改回：arm64-apple-macosx
离开构建目录也能跑：自检与 brosis-embed 都过
```

三件事：`--self-check`、`brosis-embed env`（还是过一遍 `Support/check_embed_env.py`）、
以及本机有模型目录时的 `brosis-embed selftest`。任一失败就 `fail`（exit 1）。
改回目录用 `trap … EXIT`，中途失败也不会把 scratch 留在改名状态。
默认的模型目录是 `~/Library/Application Support/brosis-m0/models`，可用 `BROSIS_MODELS_DIR` 覆盖；
目录不在就打印一行"跳过 selftest"（CI 上没有模型）。

**闸门的代价**：自检 3.1 s + `env` 0.1 s + `selftest` 2.5 s ≈ **5.7 s**
（本机连测；干净构建里 `swift build` 那一步自报 **249.40 s**，闸门占 2.3%）。

把 `app` / `core` 拷到 `~/Library/Caches/brosis-build/m2-d-fix-mut-src`，只把
`ModelResources.url` 换回"第一步就 `Bundle.module`"的老实现，再跑一次完整 `build_app.sh`：

### 1.6 `swift-transformers_Hub.bundle`：查了，本项目的两条路径**不触发**

`Hub` 目标同样有 `Bundle.module` 访问器（同样两处候选、同样 `fatalError`）。
全仓库依赖里**只有它**还有一处 `Bundle.module`
（`checkouts/*/Sources` 全扫了一遍，命中只有 `swift-transformers/Sources/Hub/Hub.swift:329`）。
调用点唯一：`Hub.fallbackTokenizerConfig(for:)`——**只有在模型目录里的 tokenizer 配置缺失 /
拿不到 `modelType` 对应配置时**才走，用来兜 `gpt2_tokenizer_config.json` / `t5_tokenizer_config.json`。

**实测（构建目录已改名，各跑一次）**：

| 走的路 | 结果 |
|---|---|
| `brosis-embed selftest`（本地 tokenizer + MLXEmbedders 加载 Qwen3-Embedding-0.6B-8bit） | `passed`，没崩 |
| `brosis --narrative-smoke`（MLXLLM 加载 Qwen3.5-4B-MLX-4bit，真生成两次） | `ok = true`，提示按 tokenizer 数出 3,203 token，没崩 |

两个模型目录里 `tokenizer.json` + `tokenizer_config.json` 都齐（`catalog.json` 里逐文件钉了
sha256，导入时校验），所以 fallback 那一支够不着。**结论：不改三方源码，也不做额外缓解。**

如果哪天真触发了，取舍是这样的（都写在这儿，省得下次重新推一遍）：

| 办法 | 取舍 |
|---|---|
| 把 `swift-transformers_Hub.bundle` 放到 `.app` 根目录 | **不可行**，本次实跑证伪：`codesign` 报 `unsealed contents present in the bundle root`，连重签都签不动；符号链接同样被拒 |
| 放到 `Contents/MacOS/` | `codesign` 把那里的 `.bundle` 当**嵌套代码**逐个校验，而它只有两个 JSON、不是 Mach-O，必然报 `code object is not signed at all`（与 metallib 那次同一个坑，见 `build_app.sh` 抬头注释） |
| 改 / vendor 三方源码 | 违反"依赖固定到确切版本、不改三方源码"的做法，升级时要重新打补丁 |
| **进程启动早期显式检查并给出可读错误** | 可行、代价小：真触发时把"这台机器上 tokenizer 兜底配置不可用"说清楚，而不是 exit 133。但现在够不着那条路，先不加，避免多一段没有触发路径的代码 |
| **靠闸门盯着**（现在的做法） | 第 4d 步的 `selftest` 每次构建都真加载一次 tokenizer；哪天依赖升级或换模型让 fallback 变成可达路径，构建当场红 |

## 3. T17 的两个代码缺陷 + 三处口径

### 3.1 `make_synthetic_queryset.py` 的 rec-08 断言指错了窗口

`build_tool_questions` 里 rec-08 的题面、`--at`、`answer`、`tool_call.window_name` 全是
**mid30m**（"第 15 天结束前的那半小时"），只有 `tool_check[0]` 的期望值写成了 `obs["last30m"]`。
改成 `obs["mid30m"]`。

**为什么一直是绿的**：语料是 10 s 一格的均匀网格，两个 30 分钟窗口都是 **180 条**
（rec-01 = last30m = 180、rec-08 = mid30m = 180）。但两者显然不是同一段时间——
同一道题的**另一条**断言 `apps.0.key` 就不一样（last30m 是 `com.microsoft.VSCode`，
mid30m 是 `com.electron.lark`）。一旦某次删除落进其中一个窗口，旧写法立刻假红 / 假绿。

**复跑**（`SCRATCH=~/Library/Caches/brosis-build/m2-d-fix-t17 sh tools/eval/run_t17_eval.sh`，exit 0）：

- `原 60 题一个字没改 + 两次生成一致` → `m1_60_unchanged: true`、
  `field_diffs_on_m1_60: []`、`holdout_flag_changed_on_m1_60: []`、`deterministic_two_runs: true`；
- `22 道工具题的 59 条断言全过` → `all_ok: true`，rec-08 的 `tool_check` 现在是
  `observations = 180`（mid30m）+ `apps.0.key = com.electron.lark`；
- 末尾 **21 项汇总自检全过**。

### 3.2 `triage_failures.py` 第二阶段分支读错了键

`eval_stage2.py` 的 `score()` 返回的字典整体加了 `score_` 前缀，键是
`score_content_ok` / `score_citation_ok`；归因脚本读的是 `score_content` / `score_citation`
——**永远取不到**。而且它把 `score_unanswerable`（"模型自己说答不出"这个事实）当成判分项，
条件还写反了（`is False` ⇒ 正常情况反而报"把可答题判成了无证据"）。

改成：读 `score_content_ok` / `score_citation_ok`；`score_unanswerable` 只在**为真**时才算一条；
理由行一律再补上 stage2 自己写的 `score_reason`（不可答题与"输出不是 JSON"这两支
`score()` 根本不写 `*_ok`，只有 `score_reason` 说得清）。`ev["stage2"]` 也换成真实存在的键。

**正反例**（夹具 `~/Library/Caches/brosis-build/m2-d-fix/triage/`，四道题都让第一阶段通过，
只在第二阶段做文章；反例脚本 = 同一份代码把键名换回修复前的写法）：

| 题 | 修复后 | 修复前（同一份夹具） |
|---|---|---|
| `t-pass`（两阶段都过） | 通过：两个阶段都过 | 通过：两个阶段都过 |
| `t-content`（内容没覆盖 must_include） | 推理错误：**答案内容不含 answer_check.must_include**；stage2 判分理由：答案没覆盖标准答案的要点 | 推理错误：**把可答题判成了无证据**（错） |
| `t-cite`（引用一条都不在真值里） | 推理错误：**引用无效（引用 2 条，落在「真值 id」里的 0 条）**；stage2 判分理由：引用的证据都不在真值 id 里 | 推理错误：**把可答题判成了无证据**（错） |
| `t-none`（不可答题却给了答案） | 推理错误：stage2 判分理由：**不可答题却给了答案** | 推理错误：**把可答题判成了无证据**（错） |

也就是说修复前**三种失败给的是同一句、而且是错的理由**；修复后三句各说各的。

`run_t17_eval.sh` 的第 6 / 8 步（变异检验的五个失败桶、100 题的六类归因）复跑照旧全过，
`det-01` 仍归「推理错误」，理由从空口白话变成
`答案内容不含 answer_check.must_include；stage2 判分理由：答案没覆盖标准答案的要点`。

## 4. T18 的措辞与引用

1. **"空名单时一次文件都不读"改成"启动时探一次，之后空名单零 syscall"**。
