口径说明（先说清楚，后面所有数字都按这个）：

- **规模**：每天 **8640 次捕获**（24 h ÷ 10 s），**30% 是新文本**，每次捕获的可见正文**平均 1500 字符**中英混排。1 个月 = 30 天，3 个月 = 90 天，12 个月 = 360 天，单设备单库。
- **8640 次/天怎么铺开**：可行性调研报告 §6.2 的同一个 8640 是按「12 h 活跃 ÷ 5 s」算的，本脚本把同样 8640 次**均匀铺满 24 h（每 10 s 一次）**。捕获次数与字节数完全一致，所以**容量结论不受影响**；受影响的只有按时间窗口取行的查询——`get_context(hours=24)` 这类查询在本报告里窗口内有 8640 条观察，而 12 h 活跃场景下同样的 24 h 窗口也是 8640 条但集中在半天，会话切分与「最近 N 小时」的行数分布因此不同，本报告的这几个延迟数字偏保守。
- **30% 的分母是全部捕获**（评审 F8 的算式 `8640 × 1500 字符 × 30%`）。实际上 13.5% 的捕获 `completeness ∈ {unavailable, excluded}`，根本没有正文，所以在「读到正文的捕获」里新文本概率被放大到 34.7%，使每天新 `text_version` 正好落在 8640 × 30% = 2592 段附近。
- **一次捕获 = 一段完整可见正文**（schema 里 `text_versions.text` 的口径是「v1 存完整原文，不分块」），所以 `occurrences` 与有正文的 `observations` 一比一。
- **字节**：全部是 UTF-8 字节。库内分项用 `dbstat` 逐 b-tree 统计**实占页字节**，不是估算系数；「原文净载荷」是 `SUM(text_versions.byte_len)`，即正文本身的 UTF-8 字节。
- **FTS 方案**：T3 推荐的 **B+E+V**（`tools/bench/results/fts_compare_2026-09-06.md` §9.2）——汉字 bigram 预处理 + `unicode61 remove_diacritics 2` + `content=''` + `contentless_delete=1`，查询时 bigram 化包成 phrase，候选再用 `LIKE` 复核。
- **冷**：全新子进程 + 全新连接，每个查询单开一条连接跑一次就关；**只清掉了 SQLite 自己的页缓存，没有清 macOS 文件缓存**（清缓存要提权），所以冷数字是下界。还有第二个成因：冷测子进程在计时之前会先跑一次 `load_params()`（内含 `ORDER BY ts DESC LIMIT 20`、`MIN(vrow) WHERE created_at >= ?` 等），这会把一部分索引页与 `observations` 尾部的数据页读进 OS 文件缓存，**等于给后面的冷查询做了部分预热**。两个成因方向一致：真实冷启动只会更慢。**热**：同一连接，先预热 1 次再连测 20 次。
- **p50 / p95**：冷 10 个样本；热的目标是 20 个样本，但 `measure_hot` 有时间预算——**单次热执行 ≥ 200 ms 的查询按 `max(3, reps × 200 / 单次毫秒)` 缩减样本数，最少 3 个**。本轮实际热样本 7–20 个、冷样本 10–10 个，逐查询的 `hot_n` / `cold_n` 都在 JSON 里；被缩减的几条在 §5 表下面单独列出。样本数少的时候 p95 实际上就是最大值，这一点在读数字时要记住。
- **单位**：本报告 §1–§6 的体积一律写作 **KiB / MiB / GiB = 2^10 / 2^20 / 2^30 字节**，字节原值在 JSON 里。**《实施计划》2.4 的「0.3 GB/月、1 GB/月、5 GB 配额」没有注明进制**，两种解释差 7%，所以 §7 的对比表同时给出 GiB 与十进制 GB 两套倍数与配额月数——建议在 2.4 里把进制定死（推荐十进制 GB，与 Finder、磁盘厂商一致）。
- **WAL 峰值**：建库全程后台每 50 ms 采样 `-wal` 文件字节取最大值。**临时空间**另有一套测法与坑，见 §4。

## 4. 临时空间（SQLITE_TMPDIR 峰值）

**测法与它的坑**：SQLite 在 unix 上建完临时文件立刻 `unlink`，所以扫 `SQLITE_TMPDIR` 目录**永远是 0 字节**（本轮实测三个规模全部 0，不是没占空间，是看不见）。这里改用「文件系统可用空间下降峰值 − 同期库文件增长」来估：把 `SQLITE_TMPDIR` 指到专用目录、`temp_store = FILE`、`cache_size` 保持默认 2 MiB，在**独立子进程**里逐个跑重活，后台每 10 ms 采一次 `statvfs`。这个数含其他进程的磁盘噪声，是**上界**不是精确值。

| 操作 | 1 个月：临时空间 / 库增长 / 耗时 | 3 个月：临时空间 / 库增长 / 耗时 | 12 个月：临时空间 / 库增长 / 耗时 |
|---|---:|---:|---:|
| ANALYZE 重算统计 | 0 B / +0 B / 202 ms | 0 B / +0 B / 492 ms | 64.0 KiB / +0 B / 1796 ms |
| 全表排序 text_versions.sha256（外部归并） | 5.1 MiB / +0 B / 127 ms | 15.1 MiB / +0 B / 271 ms | 63.5 MiB / +0 B / 969 ms |
| 全表排序 text_versions.text（最坏情况：排序键带正文） | 222.5 MiB / +0 B / 414 ms | 668.2 MiB / +0 B / 1364 ms | 2.63 GiB / +0 B / 4409 ms |
| 按应用 + 时间分组聚合（GROUP BY 溢出） | 5.5 MiB / +0 B / 115 ms | 16.3 MiB / +0 B / 233 ms | 0 B / +0 B / 853 ms |
| incremental_vacuum 回收 | 0 B / −1.9 MiB / 63 ms | 0 B / −2.4 MiB / 63 ms | 3.3 MiB / −3.0 MiB / 66 ms |
| wal_checkpoint(TRUNCATE) | 32.0 KiB / +0 B / 57 ms | 0 B / +0 B / 57 ms | 0 B / +0 B / 56 ms |

**`VACUUM` 不在上表里**：整库 `VACUUM` 需要约等于库本身大小的临时空间（12 个月规模就是 6.79 GiB 量级），这正是 schema.sql 第一行把 `auto_vacuum` 设成 `INCREMENTAL` 的理由——日常只跑 `incremental_vacuum`，不跑整库 `VACUUM`。

## 7. 与原估算（0.1–0.3 GB/月）的对比

评审 F8 引用的原可行性报告 §6.2 给的永久增长是 **0.1–0.3 GB/月**，
《实施计划》2.4 把目标定成 **0.3 GB/月、上限 1 GB/月**。

实测（1 / 3 / 12 个月三个规模高度一致，每月 **580.9 / 579.3 / 579.8 MiB**，
线性得几乎没有偏差）：

**先把进制说死**：本报告自己的数字一律 2^30 = GiB；而《实施计划》2.4 与原可行性报告写的
「0.3 GB / 1 GB / 5 GB」**没有注明进制**。所以下面凡是「实测 ÷ 目标」的倍数与「配额撑几个月」，
两种解释都列出来——结论方向（未达标、约 1.9 倍、大半年）不受进制影响，但具体数字受影响，
不要只抄一个。**建议在 2.4 里把进制定死**（推荐十进制 GB，与 Finder、磁盘厂商一致），
定死之后这张表只留一列。

| 口径 | 数值 |
|---|---:|
| 每月磁盘增长（主库 + WAL + SHM） | **580.9 MiB = 0.567 GiB/月 = 609 MB/月（十进制）** |
| 其中正文净载荷（`SUM(byte_len)`） | 215.0 MiB/月 = 225 MB/月 |
| 12 个月总占用 | **6.795 GiB = 7.30 GB（十进制）** |
| 对比原报告 0.1–0.3 GB/月 | 按 GiB 解释 **1.89× ~ 5.67×**；按十进制 GB 解释 **2.03× ~ 6.09×** |
| 对比 2.4 的目标 0.3 GB/月 | **未达标**：目标按 GiB 解释是 1.89 倍，按十进制 GB 解释是 **2.03 倍** |
| 对比 2.4 的上限 1 GB/月 | 未破上限：按 GiB 占 **57%**，按十进制 GB 占 **61%** |
| D7 的 5 GB 默认配额撑多久 | 5 GiB 口径 **8.8 个月 ≈ 264 天**；5 GB（十进制）口径 **8.2 个月 ≈ 246 天**。之后开始最旧先删 |

差在哪里，逐项拆：

1. **字符不是字节**。F8 已经指出过这一点，这里给出这份中英混排语料的实测系数：
   **1.894 字节/字符**（汉字占字符数 40.5%）。`8640 × 1500 × 30%` = 每天 388.8 万字符，
   折合 **7.17 MiB/天 = 215 MiB/月**的净正文——单这一项就已经吃掉 0.3 GB 目标的 70%。
2. **正文落到表里会放大 1.41 倍**。`text_versions` 的表数据实占 303.8 MiB，净载荷只有 215.0 MiB
   （再加上它自己的两个唯一索引共 8.9 MiB，这一项一共 312.8 MiB）。
   原因是页装填：一段 1530 字符的正文 ≈ 2.9 KiB，加上行头、`device_id`、
   64 字符的 sha256 十六进制串之后接近 3 KiB，而 `page_size` 默认 4096 —— **一页只放得下一行**，
   每行白扔约 1.1 KiB。这不是估算，是 `dbstat` 逐 b-tree 数出来的。
3. **全文索引是正文净载荷的 0.786 倍**（169.0 MiB/月）。T3 在 1.82 MiB 语料上测到的是 0.55 倍，
   到 215 MiB 语料变成 0.79 倍——**索引/正文的比值随语料增大而上升，不能拿小语料的系数外推**。
   这正是 T3 §9.5 自己留的那条「体积比例在更大语料上会变」的口子，现在有数了。
4. **事件骨架只占 16.6%**（`observations` 55.8 + `occurrences` 36.3 + `sessions` 2.4 +
   `ledgers` 1.9 = 96.4 MiB/月）。也就是说：**容量问题 83% 是正文和它的索引，不是元数据**。

### 7.1 最敏感的那个参数，恰恰是没测过的那个

存储量对「新文本比例」几乎是线性的：正文表 + 全文索引（481.8 MiB/月）随新文本条数走，
事件骨架（96.4 MiB/月）随捕获次数走。按实测分项外推：

| 新文本比例 | 每月增长 | 对 0.3 GB/月目标 | 5 GiB 配额撑多久 |
|---:|---:|---|---:|
| 30%（本轮假设，来自原报告） | 578 MiB = 0.565 GiB | 1.88×（十进制 GB 口径 2.02×） | 8.8 个月（5 GB 十进制口径 8.2 个月） |
| 20% | 418 MiB = 0.408 GiB | 1.36× | 12.2 个月 |
| 15% | 337 MiB = 0.329 GiB | 1.10× | 15.2 个月 |
| **13.1%** | **307 MiB = 0.300 GiB** | **1.00×（刚好达标）** | 16.7 个月 |
| 10% | 257 MiB = 0.251 GiB | 0.84× | 19.9 个月 |

**30% 这个数是原报告拍的，不是量出来的。** 真实的 30% 意味着：每 10 秒抓一屏，
其中 3 屏是此前从没见过的完整文本。滚动一行、光标闪一下、时间戳变一秒，
在「整屏文本按 sha256 去重」的口径下都算新文本，所以真实值可能更高；
但长时间盯着同一个不动的窗口又会让它更低。**这个数只有 M1 真机试用能回答，
而它一个人就能把结论从「超标 1.9 倍」翻到「达标」。**

### 7.2 那 1.41 倍放大是页装填，不是元数据

一行 `text_versions` 的负载 ≈ 2.9 KiB 正文 + 64 字节 sha256 十六进制 + `device_id` + 三个整数
≈ 3.0 KiB，而表 b-tree 叶页可用空间是 4096 − 35 = 4061 字节：**放得下一行，放不下两行**。
于是 77,794 行占了 77,794 页 = 303.8 MiB。`page_size` 改成 16384 之后一页放 5 行，
表数据降到 245.7 MiB（**实测 −19%**，见 §6）。

顺带一个小的：`sha256` 存成 64 字符十六进制 TEXT 而不是 32 字节 BLOB，每行多 32 字节，
12 个月是 28 MiB——量不大，但既然要改 schema 就一起改了。

| **减 OCR** | 把 OCR 兜底的应用（微信、Terminal）改成 `events_only` | 这两个应用在本轮占正文的 **25.3%**（合成语料是等概率的，见 §6.y 的警告），按比例省约 **131 MiB/月**（= 25.3% × 正文表 312.8 + 全文索引 169.0 + 出现记录 36.3；`events_only` 仍然写 `observations`，那 55.8 MiB 省不掉） | 这两个应用的历史正文彻底没有，只剩事件骨架 |
| **缩覆盖** | 关掉 1/8 的应用 | 约 **12.5%**（≈ 73 MiB/月） | 同上，按应用整块丢失 |
| **上压缩**（计划 3.4 说「容量实测证明必要时再引入」） | 正文逐段 zlib 存 BLOB | 实测压缩比 **0.597**，压缩 42 µs/段、解压 6 µs/段（2592 段/天 = 每天 0.11 s CPU，可以忽略）。正文表从 312.8 → **约 152 MiB/月**（压缩后单行 ≈ 1.8 KiB，一页放得下 2 行，页浪费从 41% 降到 17%），**`page_size` 保持 4096 时总量估算 420 MiB/月 = 0.410 GiB** | 原文不再是可直接 `LIKE` 的 TEXT，单字查询的扫描回退要先解压——按 438 MiB/s 的解压吞吐，扫 7 天窗口（≈ 50 MiB 正文）多花约 0.11 s，**比现在的 0.85 ms 慢两个数量级**，这条路要重新设计 |

`lzma preset 3` 压到 0.599，跟 zlib 一样却慢 3–9 倍——**逐段独立压缩 2.9 KiB 的小文档，
高级算法的字典优势发挥不出来**。真要更高压缩比只能上共享字典（zstd dictionary），
而那是评审 §3 明确划到 v1 之外的东西。

组合起来（都在「新文本 30%」这个假设下）：

| 组合 | 每月 | 对 0.3 GB 目标 |
|---|---:|---|
| 现状（`page_size` 4096 + bigram + 明文 TEXT） | 580.9 MiB = 0.567 GiB = 609 MB | 1.89×（十进制 2.03×） |
| + `page_size` 16384（实测） | 521.3 MiB = 0.509 GiB | 1.70× |
| + 正文 zlib（估算） | ≈ 411 MiB = 0.401 GiB | 1.34× |
| + 关掉 1/8 应用（估算） | ≈ 359 MiB = 0.351 GiB | 1.17× |

**把这三档全上，还是达不到 0.3 GB/月。** 想达标只有两条路：
把新文本比例压到 13.1% 以下（§7.1），或者承认 0.3 GB/月 这个目标是按
「字符当字节」算出来的、应该改成 **0.6 GB/月**（仍在 2.4 的 1 GB 上限内）。
**我的建议是后者**：0.567 GiB/月 意味着 5 GB 配额能留 8.8 个月，
这对「回答上周二下午我在干什么」这类问题完全够用，而为了省一半空间去砍采集覆盖
会直接损伤产品价值。真正该做的是把 D7 的默认配额从 5 GB 提到 8–10 GB
（现代 Mac 上这是可以接受的），并在设置里把「按当前速率还能留多少天」实时显示给用户。

## 10. 延迟：三个必须改的地方，都已经量过修复效果

### 10.1 精确字段通道命中 0 行时退化成全表倒序扫描（最严重）

```sql
-- 有问题的写法：谓词命中 0 行时，12 个月规模上 520 ms
SELECT o.id, o.ts FROM files f JOIN observations o ON o.file_id = f.id
WHERE f.path LIKE ? ESCAPE '\' AND o.deleted_at IS NULL
ORDER BY o.ts DESC LIMIT 20;
-- EXPLAIN QUERY PLAN: SCAN o USING INDEX idx_obs_ts / BLOOM FILTER ON f / SEARCH f ...
```

规划器为了满足 `ORDER BY o.ts DESC LIMIT 20` 选择**倒序扫 `observations`**，
边扫边回表查 `files`。命中行多的时候它扫十几行就凑够 20 条（实测 0.03 ms）；
**一条都不命中时它得把 311 万行扫完**。

| 规模 | 单条 JOIN（命中 0 行） | 两步式（先查 files，空集早返回） |
|---|---:|---:|
| 1 个月 | 冷 40.97 / 热 40.71 ms | 冷 0.49 / 热 0.00 ms |
| 3 个月 | 冷 126.19 / 热 125.99 ms | 冷 0.51 / 热 0.00 ms |
| 12 个月 | **冷 520.72 / 热 520.44 ms** | **冷 0.57 / 热 0.00 ms** |

（上表是 p50；p95 与 p50 差不到 1.5%，因为这是稳定的全表扫描，没有抖动。）

**加索引救不了**：在 `observations(file_id, ts)` 上补一个索引（48.9 MiB，建 1.0 s）之后，
规划器仍然选 `SCAN o USING INDEX idx_obs_ts`，0 行场景 523 ms，**一点没变**（§6.x）。
问题不在索引，在查询形状。修法就是把它拆成两步、空集直接返回——
`measure.py` 的 `_exact_channel()` 已经这么写了，M1 的 `search()` 也必须这么写。

### 10.2 FTS 候选阶段用 `bm25` 排序，随规模线性变慢

T3 §9.4 给的查询规划是 `ORDER BY bm25(text_fts) LIMIT 200`。对**高频词**来说，
这要求把整条倒排表读完再排序：

| 查询 | 1 个月 | 3 个月 | 12 个月 |
|---|---:|---:|---:|
| `采集覆盖率`（bm25 排序，热 p50） | 21.96 ms | 60.88 ms | **225.11 ms** |
| `采集覆盖率`（rowid 倒序，热 p50） | 1.31 ms | 1.22 ms | **1.33 ms** |
| `checkpoint`（bm25 排序，热 p50） | 17.11 ms | 48.46 ms | **186.16 ms** |
| `checkpoint`（rowid 倒序，热 p50） | 0.63 ms | 0.64 ms | **0.67 ms** |
| `tools/bench/fts_compare.py`（bm25，热 p50） | 12.27 ms | 31.62 ms | **117.12 ms** |
| `tools/bench/fts_compare.py`（rowid 倒序，热 p50） | 1.28 ms | 1.39 ms | **1.42 ms** |

`text_versions.vrow` 是单调递增的，所以 **`ORDER BY rowid DESC` ≈ 时间倒序**，
FTS5 可以从倒排表尾部直接取前 N 条，**延迟变成规模无关**（12 个月比 1 个月还快一点点）。
低频词两种排序都在 4–5 ms，没有差别。

代价是排序质量：bm25 是相关度序，rowid 是时间序。对「我上周看的那个东西」这类问题
时间序反而更对；真要相关度，就先用 rowid 倒序取一个较大的候选窗口（比如 2000 条）
再在候选里算 bm25。**加 `rowid >= ?` 的时间下界没有额外收益**（12 个月冷 p50 2.11 → 1.98 ms），
因为 rowid 倒序 + LIMIT 本身就已经短路了，不必再套一层窗口。

### 10.3 `sessions` 的区间查询用不上索引

```sql
-- 有问题：idx_sessions_range 是 (device_id, start, "end")，
-- 这个谓词只能用上 start <= ctx_to，等于扫掉几乎所有会话
WHERE device_id = ? AND "end" >= ? AND start <= ?
-- 修法：给 start 补一个下界（会话长度上界，这里用 24 h）
WHERE device_id = ? AND start >= ? AND start <= ? AND "end" >= ?
```

| 规模 | 原写法（热 p50） | 补下界（热 p50） |
|---|---:|---:|
| 1 个月 | 0.47 ms | 0.07 ms |
| 3 个月 | 1.38 ms | 0.07 ms |
| 12 个月 | **6.42 ms** | **0.07 ms** |

原写法随规模线性变慢，补一个下界之后规模无关。会话长度上界应该是 3.7 里那个
「停留上限 90 s」的可配置参数，不该硬编码 24 h。

### 10.4 修完之后的延迟全貌

| 类别 | 1 个月 冷/热 p95 | 3 个月 冷/热 p95 | 12 个月 冷/热 p95 | 随规模 |
|---|---:|---:|---:|---|
| 精确字段（命中，5 条查询） | 0.90 / 0.13 ms | 0.72 / 0.09 ms | 0.76 / 0.14 ms | **无关** |
| FTS（低频词，4 条） | 2.58 / 1.55 ms | 4.39 / 3.32 ms | 5.51 / 4.53 ms | 弱增长（≈ log） |
| FTS（高频词，rowid 倒序，3 条） | 2.23 / 1.39 ms | 2.35 / 1.47 ms | 2.28 / 1.49 ms | **无关** |
| 单字查询走 7 天扫描回退 | 1.06 / 0.19 ms | 0.91 / 0.17 ms | 0.95 / 0.21 ms | **无关**（窗口固定） |
| `get_context(hours=24)` 三段合计 | 3.15 / 2.44 ms | 4.91 / 4.33 ms | 9.99 / 9.67 ms | 增长，主因是 10.3 |
| app + 7 天范围扫描（3 条） | 1.97 / 0.85 ms | 1.69 / 0.85 ms | 1.67 / 0.89 ms | **无关** |

**修完三处之后，12 个月规模上没有一条查询超过 10 ms**，离 300 ms 的预算差 30 倍。
F8 担心的「不能只拿首月规模承诺所有查询 <300 ms」在这轮成立——
原样照 T3 §9.4 实现的话，12 个月上确实有 225 ms 和 521 ms 这样的数——
但成因是查询形状而不是数据量本身，改掉之后规模不再是威胁。

**冷热差别很小（冷 0.6 ms / 热 0.05 ms 的绝对差不到 1 ms），
是因为 macOS 的文件缓存没清**（清缓存要提权，见 §1 口径）。
第一次开库、磁盘真冷的场景本轮**没有覆盖**，这是这份延迟数据最大的口径缺陷。

## 11. 这轮没做 / 不能拿来当结论的

1. **`powermetrics` 成对测量一个真实数字都没有。** `tools/bench/powermetrics_pair.sh`
   只走通了 `--dry-run`。原因有两个，都不是脚本问题：**(a) M1 的记录器还不存在**，
   B 臂没有东西可开；**(b) `powermetrics` 必须 root，要你本人输密码**，Agent 不能代劳。
   2.4 的「资源」一行因此**未验收**。
2. **合成语料不是真实屏幕。** 语料是 36 条中文 + 14 条英文 + 10 条代码 + 路径 URL
   按权重拼出来的，词频分布、重复模式、行长分布都和真实屏幕不一样。
   §6.y 的应用分布是**等概率生成的**，不代表真实使用。
   「1.894 字节/字符」「压缩比 0.597」「索引/正文 0.786」这三个系数都依赖语料，
   M1 真机试用后必须复测。
3. **30% 新文本比例是假设，不是测量**，而它是最敏感的参数（§7.1）。
4. **明文库，不是 SQLCipher。** 加密后的页面开销、FTS5 在 SQLCipher 上的表现、
   `dbstat` 是否可用，都要在 E6 选定构建之后复跑一遍这套脚本。
5. **单设备单库。** D17 的跨设备同步会把另一台机器的行也导进来，
   同步 2 台机器就是两份容量。本轮没测同步带来的额外索引与冲突开销。
6. **缩略图、模型资产没有实测字节**（§8.1 只有算式）。
7. **没测删除 / 配额过期在 12 个月规模上的耗时。** T4 的 E3 在小库上验了语义正确，
   但「配额满了要删掉最旧的一个月」在 6.8 GiB（7.3 GB 十进制）的库上要花多久、`incremental_vacuum`
   要跑多久、期间能不能同时查询，这些都没量。这是 M1 之前该补的一项。
8. **临时空间的最坏情况值得单独记一笔**：对正文列做全表排序，
   12 个月规模上要 **2.63 GiB 临时空间**（≈ 正文净载荷的 1.04 倍），耗时 4.4 s。
   任何 `ORDER BY text` 或对正文的大排序都要按这个量准备磁盘，
   低磁盘时应该直接拒绝执行而不是把盘写满。整库 `VACUUM` 更贵（≈ 库本身大小，
   12 个月就是 6.8 GiB），这也是 `auto_vacuum = INCREMENTAL` 必须留着的理由。
9. **`ledgers` 的证据数组是全量观察 id**（1 个月 1.9 MiB、12 个月 25.9 MiB）。
   量不大，但一天 8640 个 id 塞进一个 JSON 数组不是好设计，M1 改成区间表示更合适。

## 12. 一句话结论

按「8640 次/天 × 1500 字符 × 30% 新文本」这套假设，**单设备单库每月增长 0.567 GiB，
12 个月 6.8 GiB**——是原报告估算的 1.9–5.7 倍，超 2.4 的 0.3 GB/月目标 89%，
但仍在 1 GB/月的上限内，D7 的 5 GB 默认配额能撑 8.8 个月。
**容量的 83% 是正文和它的全文索引**，剩下 17% 才是事件骨架；
最敏感的参数（新文本比例 30%）是假设值，M1 一测就可能把结论翻过来。
**延迟在 12 个月规模上完全不是问题**——三处查询写法改掉之后所有查询热 p95 < 10 ms，
问题从来不是数据量，是 `bm25` 全表排序、`JOIN + ORDER BY LIMIT` 的退化扫描
和用不上索引的区间谓词这三种写法。
